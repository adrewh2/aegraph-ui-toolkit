# Memory: a massive project in one tab

A review of what the app holds when the project is big, measured on the largest real one — the Toronto street
trees demo, 689,357 entities, a 38 MB `.aeb` — in a production build. It follows
`performance-2026-09-26-two-million.md`, which measured the store alone (≈770 B an entity); this one measures the
whole tab: opening, saving, committing, reloading, searching, and every page, and what each leaves behind.

## How it was measured

`vite preview` of `dist/` (dev-mode React roughly doubles every number), driven by `mcp/drive.mjs` with a fresh
Chrome profile. At each stage: two `HeapProfiler.collectGarbage`, then `Runtime.getHeapUsage` — the JS heap that
survives, which is what a tab keeps. Peaks during an operation are sampled from Node every 150 ms while it runs; a
long synchronous task hides what happens inside it, so a sampled peak is a floor. The retained heap by allocation site
comes from `HeapProfiler.startSampling` / `getSamplingProfile`.

Two cautions for the next person. Run each measurement on its own bridge port far from anyone else's (the 94xx
range was used here): a bridge server whose port is taken binds the next one and tabs search the range, so a second
session's headless tab can answer your tool calls while CDP measures yours. And a page restores what was typed into
it (the table's quick search is remembered), so reuse a profile knowingly.

## What was found and fixed

All numbers: 689k trees, JS heap after GC.

| | before | after |
| --- | --- | --- |
| open the bundle — peak (sampled) | ≥ 583 MB | ≥ 512 MB |
| open — settled | 362 MB | 352 MB |
| after a tour of every page | 504 MB | 364 MB |
| the first commit — peak, time | ≥ 1,138 MB, 15.2 s | ≥ 560 MB, 6.7 s |
| reload, once the project has a commit | **950 MB** | **354 MB** |
| one text search (the assistant's, the store's) | +386 MB for good | +433 MB, gone 30 s after |
| one quick search in a table | +211 MB for good | gone 30 s after |

1. **History rebuilt HEAD's tree from the commits' content** (`history.ts › rebuild`). The first commit of a big
   project *is* the project, so after a reload the unsaved-changes badge read it back from IndexedDB and the blob
   cache kept it: a second full copy, for the life of the page. Autosave is on by default, so every edited big
   project reached this on its next reload. Now each commit also writes a record of just its ids and hashes (the
   `trees` store, `BlobStore.hashes`), one joined string each; the tree is rebuilt from those, keyed by the store's
   own id strings. A commit from before the record is read once and given one. The blob cache is weighed in
   entities (50k), and a blob past that is kept only for the burst it was read for (15 s).
2. **A commit was a structured clone of the whole project on the main thread.** A commit past 2,000 entities is
   stored as the pack, in chunks of 20k with the event loop between them.
3. **The store's search text was kept on every entity after one search** (`searchTextOf`): 386 MB — about 560 B a
   tree, the lower-cased text plus the property on each object. A search without it takes ~0.7 s over 689k, with
   it ~0.2 s (1.4 s to build), so it stays a cache for a burst: every entity given a text is noted, and they all let
   it go 30 s after the last was asked for.
4. **The table's quick-search text per row** (`EntityTable.tsx › rowText`), a module-level `WeakMap` keyed by
   entities that live as long as the store: 211 MB after one keystroke. The map is replaced when idle for 30 s.
5. **Opening a gzipped bundle held the output twice** (`gunzip.ts`): every chunk kept, then a buffer of the total
   allocated and filled. Now one buffer, sized from the gzip trailer (a hint — it grows when a multi-member file
   says less) and written as chunks arrive; the input is streamed without the copy a `Blob` makes; the compressed
   file is let go before the import (`openBundleBytes`), which is the peak.
6. **The pack's string table was two bytes a character** because 82 of its 1.9 million strings hold an em dash
   (`bytes.ts › StringTable.read`): V8 keeps a string one byte a character only when all of it fits in Latin-1, and
   a slice shares its parent. The ASCII strings are now joined and sliced on their own.

7. **Every Unigraph tab ever opened kept its keys** (`aegraph:explorer:v1:<session>`, `…positions:v1:<session>` and
   its IndexedDB set, `…detail-tabs:<session>`). At boot, after the Library is read and before any page mounts, the
   sessions nothing names — stored UI state, a pick, a saved `workstation` entity — are removed (`heldPositions.ts ›
   sweepExplorerSessions`), and position records left without a marker after them. The explorer's `gx:*` timings go
   through `lib/measure.ts`, which keeps the last 500 of each, instead of piling up on the performance timeline.

## What is still open, largest first

Estimates are from reading the code at 689k entities unless marked measured.

1. **The whole Library is in memory whatever project is open.** Measured: with the 349-entity system map open and
   the trees in the Library, the tab holds 313 MB. `persistence.load` reads every page into the one store at boot.
   Loading a project's entities when it is opened (the pages are already per-write; they would need to be per
   project) is the largest change left and the one that makes "a big project costs nothing until you open it" true.
2. **An entity is ~450 B as an object** (store + indexes, measured here as 352 MB / 689k ≈ 510 B with everything).
   The two-million review's stages — relationship endpoints as CSR, epoch dates, interned ids, columns — apply.
   Cheap part: the pack decoder makes a new `tags` and `meta.projects` array per entity; interning the (few)
   distinct lists saves ~30 MB here (`pack.ts › Decoder.entity`).
3. **Script sandboxes keep their snapshot.** The JavaScript worker and Pyodide keep the last dataset they were
   handed (QuickJS reserves up to 6× the JSON as WASM memory, which never shrinks); a Visual script's frame is
   detached, not stopped, when the Scripts page goes. Terminate a worker idle for a minute and on unmount; default a
   script's snapshot to its `data.types`.
4. **Unigraph draws from every node in the project.** Measured: +95 MB on a 50-node scene of the trees (the engine
   holds all 688,737 and shows 50), released when the page is evicted from the kept pages. 2D and 3D are separate
   explorers with separate copies. `nodeById`, `slice.degree`, `styles.nodes` and the position store are
   688k-entry `Map`s (~14 MB each) where typed arrays by engine index would do.
5. **The map keeps ~28 MB after it is left** (measured): the pin index is keyed on `allGeo`'s array, which the
   module cache holds for the life of the store; the hidden globe builds its track layer for every point even when
   the globe is never shown. Own the index in the canvas; mount the globe on first use.
6. **A cross-tab reload holds two copies** (`persistence.ts`): an upsert of 500+ entities announces `reload`, and
   another tab decodes everything while its store is still full. Announce the pages written, or clear first and
   stream.
7. **Smaller, each 10–30 MB:** `versioning.ts › hashCache` (a hash string per entity, kept), the working diff's
   `added` map on a never-committed project, `scopeOf` copying the project's id set, the JSON import path holding
   the text, the parsed document and a normalised copy at once.

## The rule this leaves

A cache over every entity is a cache for a burst, released when idle — never a second copy kept for the page's
life. A tab dies at its peak, so any path that holds two full representations at once (bytes and entities, the store
and a blob, the old store and the new) is the thing to design out.
