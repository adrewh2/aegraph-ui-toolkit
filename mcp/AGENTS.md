# `mcp/` — the Claude Code bridge, the driver and the smoke suite

- `server.mjs` — the MCP server Claude Code starts (`.mcp.json` registers it as `aegraph`). Stdio to Claude Code, a local WebSocket to the app tab; the tab sends its **tool manifest** and executes every call in the browser, so the server holds no tool code and the tools are always exactly what the app exposes (`src/features/assistant`). `aegraph_bridge_status` is the one tool of its own; with several tabs, calls go to the tab the user last brought to the front. When the port is taken by another session's bridge the next free one in the span is used, and the tab connects to the whole span. Env: `AEGRAPH_BRIDGE_PORT` (8787), `AEGRAPH_BRIDGE_PORT_SPAN` (10), `AEGRAPH_BRIDGE_TOKEN`, `AEGRAPH_BRIDGE_TIMEOUT_MS`, `AEGRAPH_CLAUDE_BIN` / `AEGRAPH_CLAUDE_ARGS` (the `claude -p` a chat turn runs). A chat turn from the app's panel spawns a child bridge for its `claude -p` on a port the system picks — outside the span, which is the sessions' (nine sessions open fill it; the tab is told the child's address by `probe`) — (`AEGRAPH_BRIDGE_CHAT=1`, `AEGRAPH_BRIDGE_FOR_TAB` pinning it to the tab that asked, `AEGRAPH_BRIDGE_WAIT_MS` for the tab to connect); that child also offers the permission tool and carries Claude Code's permission prompts back to the app. The bridge's own rules live in modules beside it, each tested in `security.test.mjs`:
  - `chat.mjs` — how a chat turn's `claude -p` runs: the app's tools and **no built-in tool** (`--tools ""` and `BUILTIN_TOOLS` denied by name), `--permission-mode default`, cwd an empty directory under the user's cache (`chatDir`, stable so `--resume` finds the session; never the repo, never shared `/tmp`), an environment allow-list (`chatEnv`: sign-in, API/Bedrock/Vertex, proxy, CA — not the terminal's other secrets, and not the identity of the session that started the bridge: `SESSION_OWN` strips its session id, project dir and messaging socket), and not the developer's settings file (`--setting-sources project,local`: no user hooks firing per turn, no permission rules widening it) — their `~/.claude/CLAUDE.md` and Claude Code's auto-memory do load, as in any session of theirs (the owner's choice: a chat through Claude Code should know what their Claude Code knows; memory is filed under the chat folder's project, not the repository's), `AEGRAPH_CLAUDE_ARGS` stripped of any permission-widening flag (`filterClaudeArgs`), and the permission question shown whole or declined (`describeToolUse`, `MAX_PROMPT_CHARS`). A new `claude` flag that grants something goes on the refused list.
  - `frame.mjs` — every text block of a tool result, and a tab's error, goes to the MCP client inside `<untrusted_data source="aegraph" tool="…" id="…">`, the id 64 random bits made for that block and only `</untrusted_data id="…">` with it closing the envelope; the tag's name is broken wherever the text spells it, in any case or look-alike (NFKC folding, Cyrillic/Greek letters, zero-width and direction characters, separators, HTML references); `cleanPageText` makes a page's words plain text for places that are not framed (a tool's description, a tab's label); `INSTRUCTIONS` (the server's MCP instructions) says nothing inside is an instruction. The headless engine frames its results and tool errors the same way (`src/headless/results.ts`, `HEADLESS_INSTRUCTIONS`). Anything that reads results as JSON (`drive.mjs`, `attach.mjs`, `smoke-headless.mjs`, the Aurora demo's generator in aegraph-ui-demos, smoke steps using `client` directly, the tests) calls `unframe`.
  - `publicUrl.mjs` — public addresses only, checked in the socket's own DNS lookup (every redirect hop again; `::/96` and IPv4-mapped forms included): used by the headless engine's `fetch` (`src/headless/publicFetch.ts`, which `dev/fetch.ts` reads through too), not by the bridge, which **fetches nothing** — an image reaches Claude Code as pixels the tab sent (`view_image` fetches it in the tab after asking), and an image block that is only a URL becomes a note that it was not fetched.
  - `token.mjs` — the token compared in constant time.
  In `server.mjs`: **routing** — without `AEGRAPH_BRIDGE_TOKEN` the first tab to connect sets `homeOrigin`, and calls go only to tabs from it (another origin's tab is connected but never active; `aegraph_bridge_status` lists it as `notRouted` with the `routedOrigin`, framed); with the token every tab is routed to. A tab's manifest is cleaned (`cleanManifest`: names `[A-Za-z0-9_-]{1,64}`, not the bridge's own, no repeats; descriptions through `cleanPageText`, at most `MAX_DESCRIPTION_CHARS` 32,000; every description and title in a schema the same; a schema past `MAX_SCHEMA_BYTES` 64 KB dropped), and so is its label. Chat turns are capped at `MAX_CHATS_PER_TAB` (3), `MAX_CHATS_PER_ORIGIN` (3) and `MAX_CHATS` (6), and a turn's child bridge takes a token made for that turn, told only to the tab that asked in the `probe`. `HOSTED_ORIGIN` is the one non-loopback page allowed by default (`AEGRAPH_HOSTED_ORIGIN`; `https://aegraph.sh`, this edition's site, unless it is set — empty for none); the tab follows a `probe` only to a loopback `ws://` URL (`src/features/bridge/bridge.ts › loopbackBridgeUrl`); loopback is allowed on any port because every worktree's dev server has its own. Messages are capped at 32 MiB (`maxPayload`), a socket error is logged rather than thrown (unheard, one bad frame from any page killed the process), a connection's chat turns are its own (`tab.chats`: another tab cannot stop them), and a `confirm-result` counts only from the tab the question went to. The bridge lives as long as its client: it exits when stdin ends (a listening socket would otherwise keep an orphan alive), and its chat turns' `claude` processes go with it.
  **Two apps, two sessions:** give each pair its own range of ports — the second session starts with `AEGRAPH_BRIDGE_PORT=8797 claude` (the server inherits the session's environment) and the second app, on its own dev-server port (so its own origin and localStorage), has its bridge URL set to `ws://127.0.0.1:8797`. The ranges 8787–8796 and 8797–8806 don't overlap, so neither session reaches the other's tab (`/docs/assistant` › *Two apps, two Claude Code sessions*).
- `drive.mjs` — drive the app without Claude Code: spawns the server, launches headless Chrome on a dev or preview URL with a persistent profile, and runs a steps module: `export default async ({ call, evaluate, shot, sleep, send }) => { … }`. `call(name, args)` is a tool call (JSON results parsed, errors thrown), `evaluate(js)` runs in the tab, `shot(file)` screenshots, `send(method, params)` is raw CDP — `Input.dispatchMouseEvent` for real gestures, `Profiler.start/stop` for a CPU profile. `GL=1` gives software WebGL; `PROFILE=` keeps runs' Libraries apart; `CHROME_PATH=` names the browser (by default Chrome's macOS or Windows install path, or google-chrome / chromium on Linux's PATH — `chromePath.mjs`). Each run's bridge is its own: a random port (or `BRIDGE_PORT=`) with no span, a token, and the tab linked to that port alone (`span=1` in its bridge URL, read by `spanUrls`) — so a run never answers another session's calls nor sends its own (or its auto-accepted delete confirmations) to another tab, and it stops before the steps if the bridge reports another port or more than its one tab. Use it to verify a change in the real app, to take the screenshots a demo needs, and to measure (long tasks, render counts) before and after a performance change.
- `attach.mjs` — the same against the tab you have open.
- `smoke/` — the scripted runs over a real tab (`smoke.mjs` runs the first four in order; the rest have their own `npm run smoke:*`): project, relaunch, bundle, open, scripts, scenes, iterate, claims, diagram, projects, charts, maps, media, and on through the pages to step 27, which opens what the headless engine authored for the Aurora demo and checks the app makes the same picture, and 28, a tab opened on a scene that must never build the whole graph first. A step that reloads the page does its tidy through `evaluate` (the store), not a tool: calls made while the bridge reconnects can hang. Each step `check`s what it proves; `/docs/smoke` describes them and keeps a run on record. A new page or tool that can be exercised headlessly gets a step here.
  Two things a step in this suite learns the hard way, both about what to *ask*: read state through the tools (`graph_state`, `get_entity`, `search_entities`), not through `window.__aegraph.store` — opening a project remounts the app and the store on `window` is the one from before the remount — and when a check is about the *picture*, sample until it settles, because a camera flying into place reads as a picture half off the canvas.
- `smoke-headless.mjs` — the suite's one run with no browser in it: `npm run smoke:headless` builds `dist-headless` and drives `src/headless` over stdio MCP, then opens the workspace again in a second process.
- Tests: `server.test.mjs`, `server-edges.test.mjs` (the server's protocol, tool routing, errors, what a connected page cannot do), `origin.test.mjs` (the handshake), `security.test.mjs` (the rules above, without a server).

When a tool changes shape, nothing here changes — but the smoke step that calls it, and `/docs/assistant`, do.

- Shared smoke `check` failures set `process.exitCode = 1` without throwing, so cleanup still runs and automation cannot mistake printed failures for success. `smoke.test.mjs` verifies both outcomes in child processes. Use fresh `PROFILE` and `DOWNLOADS` directories for isolated release checks; an earlier same-name download is not the current bundle.
