# Assistant & MCP

The in-app assistant (the panel on the right) and the **Claude Code bridge** use one tool set. Every capability in these docs is reachable through it, so a sentence like *"move all my documents into a grid at the top-left, x = citations, y = references, colour by most recently edited"* is two tool calls (see [Position layouts](/docs/positions#example)).

## What the assistant sees and does

Every message carries an `<app_context>` block: the route, the open project, the document or media on screen, the selected text, Unigraph (filter, layout, style, the selected nodes with their ids, what the detail pane shows), every table on screen (what it is narrowed to, how many rows, which are selected) and the open tabs of each pane host. So "these", "this graph" and "the selection" resolve without a lookup, and the assistant is expected to act — filter and lay out the graph, open a table, select and frame entities — then say in a sentence what changed.

**These docs are readable too.** The `docs` tool lists the pages with their sections, reads a page or one section as Markdown, and searches all of them for the sections that contain every word — so "how do position layouts work?" is answered from the same text you are reading, not from memory. When a documentation page is on screen — at `/docs/…`, or as the active tab of a Workstation pane — the context names it (a docs_page line), and "this page" means it; the assistant reads it with `docs`, not `read_document`, which is for your own documents. A question is answered in the chat, with a link to the page and section it came from and an offer to open it; the assistant opens a docs page (`docs` with `open` — a tab beside what you have when the Workstation is on screen, the Documentation view otherwise) only when you ask to see it.

**Several chats at once.** The panel has tabs (and the [Chats page](#the-chats-page) shows every chat full size): **+** opens a new chat in front, a tab's × closes it, a double-click renames it (otherwise the first message names it), and a pulsing dot marks a chat still working while another is in front. Each chat is its own conversation — its own transcript, API history and Claude Code session — and every tab comes back after a reload. Voice control, *Ask about this* and the tools talk to the chat in front; saying **new chat** opens a tab. Over MCP the `chat` tool lists, opens, starts, closes, renames and deletes them.

**Chats are in the project.** Every chat you speak in is recorded as a **conversation** entity (source `assistant`, tag `assistant:chat`) in the project that was open when it started — the same type the ChatGPT transcripts use, so it sits in Conversations, is searched, linked, annotated and exported with the project, and the assistant can find earlier chats with `search_entities`. The record is written when you send a message and again when the reply is complete — not while a reply streams, which would rewrite it, and set off autosave, many times a second — and it holds what was said and what was done (each tool call, with its input and a short result). The transcript in the panel survives a reload by its own save, a moment after each change, so even a reply interrupted mid-stream comes back as far as it got. A tool call that was running when the page reloaded — or when Claude Code's turn ended before its answer came back — comes back marked **outcome unknown**, not failed: the call had been sent, and often finished; the card keeps its input as far as it had arrived and says to check before running it again. Closing the tab forgets the transcript in the panel, not the record; deleting the chat (on the [Chats page](#the-chats-page)) removes both. A chat nobody has spoken in is not recorded.

**Chats belong to their project.** A chat belongs to the project that was open when it started, and is recorded there even if you have moved on by the time its record is written. With a project open, the panel's tabs, the Chats page, the number beside **Chats** in the sidebar and the chat voice and *Ask about this* talk to are that project's; switching project brings forward the chat that was in front there last, or a fresh one — a chat still running in the project you left goes on running. With no project open (the Library), every chat is there.

**Download the transcript.** The download button in the panel's header writes the chat in front as a file: **Markdown** — every user turn and reply, every tool call with its input, its full result (pretty-printed when it is JSON, cut past 60,000 characters) and how long it took, questions and confirmations with their answers, a table of the tools used with call counts, failures and time, and the token counts — or **JSON**, the same plus the conversation as the API saw it. It is the material for looking back at how a task went — which tools were called, in what order, what came back, where time went — and improving the tools and prompts. Over MCP: `chat {action:"transcript", format?}` returns the same text for the chat in front (or `id`).

**Resuming.** Open a recorded chat (Conversations, or the entity anywhere) and **Resume in the assistant** continues it, with everything said so far: its own tab comes to the front if it is still open; otherwise a new tab is seeded from the record — the transcript as it was shown (tool calls as cards), a history rebuilt from it for the model, and the Claude Code session it was in, which is resumed when the same machine still has it. The continued chat keeps recording to the same entity. Over MCP: `chat {action:"resume", id:"assistant-chat:…"}`. A chat from another machine, or a project bundle, resumes the same way — the model picks up from the transcript rather than from a live session.

**Memory.** What the assistant is told once it keeps: a preference ("dark colours for people"), a convention ("segments are called passages"), what you are working on, anything you ask it to remember. The notes live in the entity system as the **Assistant memory** document of the open project (tag `assistant:memory`, one per project, and one for the whole Library outside any project) — open it in Documents to read or edit it — and reach every turn through an `<assistant_memory>` block in the context. The `memory` tool reads it, adds a note (shown to you first, kept only with your yes), forgets lines (more than one is shown to you and asked about), or rewrites it (a rewrite shows you before and after and asks); an edit to the memory document through the document or entity tools is shown and asked about the same way. Claude Code's own memory files are its business; this one travels with the project — but only a memory written **in this browser** is the assistant's own. One that arrives in a bundle, an import or a demo is read as *shared notes*: carried into the turn marked as someone else's writing, never obeyed and never written to, because a planted memory would otherwise be an instruction in every turn. A bundle that would replace the assistant's own memory is not opened. The first note the assistant keeps starts this browser's own.

**Your words, and everyone else's.** Only what you type or say is an instruction. Entity labels and fields, documents, selected text, imported bundles and datasets, web pages and every tool result are data other people may have written, and the assistant is told so: text in them that reads like an order ("ignore your instructions", "fetch this URL") is not followed, and it says when it sees one. The things such text would want are put to you in the app instead, whoever is asking — the panel, Claude Code over the bridge, a headless client:

- **Fetching a URL a tool was handed** — `import_graph`, `map_import`, `project_open_bundle`, `create_image`, `view_image` (the assistant looking at a picture on another site), or an address `create_entity` / `update_entity` would put where a view loads it (an image, a thumbnail, a screenshot) — goes straight through only on this site's own origin. Anywhere else needs **Third-party services** on and your yes, naming the host; a URL that is not http(s), or carries a password, is refused. With no page (the headless engine) an address on this machine or its local network is refused outright.
- **Opening a bundle over your work**: `project_open_bundle` with a bundle that would replace entities you have says how many, names three of them, and marks it in red when documents would lose most of their text.
- **Turning the microphone on** (`voice {listen}`), every time; the yes lasts for that page only.
- **Changing Third-party services** (`account set`).
- **Losing work**: a restore or discard that would throw away unsaved changes (asking for `unsaved: "discard"` still asks), reverting an entity, taking entities out of a project (`project_remove`), a `write_document` that drops most of a document's text, deleting a slide, a block, a point or a chapter with text of its own (or a story or a deck with what hangs from it), and any change to the memory — as well as every delete.

A question names what it is about in quotes, on one line, clipped, so a label cannot pass itself off as part of the question. When a tool or Claude Code asks, the dialog starts on **Cancel** and its yes cannot be pressed for half a second after it appears or changes; several questions wait their turn rather than replace one another.

**With your own key, the assistant can search the web** (Anthropic's server-side `web_search`, a few uses per turn, billed per search) for what the workspace does not hold — a fact, a definition, a current event; the workspace's own content still comes from its tools. A spoken turn runs at low effort whatever the setting, so the answer comes quickly.

**Reading the web.** Paste a link and the assistant can read it with `web_fetch`: a page as readable text with its title, links and the scripts it loads, an API's JSON, a CSV, a script's source. It is how the assistant gets from a link to the data behind it. Many pages that show data are apps whose HTML is an empty shell their scripts fill from an API, so each page read also lists the URLs in it that look like data files or APIs, and the JSON it carries inline for its scripts, and the assistant can search the page and every script it loads, in one go, for how it loads its data (`find` with `scripts`: the loading code is usually in one large shared bundle among dozens) and then read that API. A share link to a Cosmograph map goes page → scripts → the project's API → a signed link to its Parquet file that way. A binary file — Parquet, an image, an archive — is described (its type and size) and not downloaded; if there is an importer for its format the assistant hands it the URL. Reading another site asks you first, naming the host, once for the conversation (a site is usually several requests; over the bridge, once for the Claude Code session) — and again for an address there whose query or path is long, which is how data would be sent out in a URL; each other host is asked about separately, a page that redirects to a host you have not said yes to is asked about before the redirect is followed, and nothing is read with Third-party services off. Only GET: nothing is posted anywhere, and no cookie or sign-in of yours goes with the request. Most sites do not let a browser page read them directly; when the browser is refused and the app is running locally, the dev server reads the page for you through its own `/api/fetch`, which fetches public addresses only (never this machine or its network), 3 MB of text at most, in 20 seconds. A deployed copy has no server, so there such a page cannot be read, and the assistant is told so. What comes back is someone else's text and reaches the assistant marked as such.

**Attaching files.** Images, documents and data files go into a chat with the paperclip beside the composer, by dropping them anywhere on the chat, or by pasting an image into the composer. They wait above the message as chips (a thumbnail for an image, a table for a data file, the name for a document; × takes one back out) until you send, and a message can be files alone. On sending, each becomes an entity in the open project, through the same importers as the pages: an image (PNG, JPEG, GIF, WebP, SVG, AVIF, up to 10 MB) is an **image** kept inline, a Markdown or PDF file (a PDF up to 15 MB) is a **document**, and a table is a **dataset** ([Datasets](/docs/datasets)) — a CSV (comma-separated, or semicolons when its header uses them) or TSV file, gzipped or not, an Excel workbook (`.xlsx`: every visible sheet with cells becomes a dataset of its own, named *workbook · sheet*; the first row with anything in it is the header, a number in a date format is its date, a formula its last computed value) or a Parquet file (every column, nested values as JSON). A **text file** (`.txt`) can be either, so the chat asks as you attach it: **Document** or **Dataset** — and for a dataset, what separates its columns (comma, tab, semicolon, pipe, spaces, or any other string you type; the file's own is guessed first) and whether its first row is the header, with its first rows shown as that choice reads them. The message waits until each text file is answered. A data file is read with limits — up to 50 MB, 200,000 rows, 500 columns and 5 million cells, and no more than 256 MB once decompressed — and one past a limit is refused with a sentence saying which, rather than read half-way or left to stall the tab. The message tells the assistant what was attached, by id — for a dataset its size and its columns — so it looks at a picture with `view_image`, reads a document with `read_document` and a dataset's rows with `dataset {action:"get"}`, like anything else in the project. What is written inside a file is data, like any document, not instructions. The sent message shows the files as chips that open them (on the Chats page, beside the chat; a dataset on the Datasets page elsewhere), and they count among the chat's [artifacts](#the-chats-page). Anything else — a Word file, say — is named and turned away before it is sent. Over MCP, the same comes in through `create_image` with the picture as a `data:image/…;base64,…` URL, `create_document` with a PDF as `data:application/pdf;base64,…` (or Markdown and text as `content`), and `dataset {action:"create", file, filename}` with the data file as a `data:` URL — or delimited text as `csv` with its `delimiter` and `header`.

**Stopping.** The stop button (■, where the send button is while the assistant works), or saying **stop** with voice on, ends the turn at once: what was written so far stays, a tool call still running is marked cancelled, and the transcript says **Stopped** — quietly, because it is what you asked for, not an error. A question or confirmation the assistant was waiting on reads *Not answered — you stopped the chat* rather than *Declined*, and the chat's record keeps both. The next message starts a new turn in the same conversation.

**Ask about this** is in every context menu (table rows, the graph's nodes and edges, the explorer's Nodes/Edges tables, documents, images, videos, audio, diagrams, maps) and on each Insights finding (**Ask**): it opens the assistant with a question about that entity, the selection, or the finding, naming ids so the answer is exact.

## The Chats page

**Chats** in the sidebar (between Workstation and Entities, `/chats`) is where chats live. On the left, the open project's chats: the ones **Open** in this browser, every one recorded in the project under **Earlier**, and **Imported** transcripts (ChatGPT's) in it, each with when it last moved and how many messages it has, the open one raised as a card above the others; a search narrows the list. A new chat joins the list, and the count beside **Chats** in the sidebar, with its first message; until then the list reads *Your chats will appear here* if there is nothing else in it. Right-click a chat to open, close or **delete** it: deleting, once you confirm, removes the chat for good — its tab, its transcript and its conversation entity in the project (an imported transcript too) — while what it made stays.

**Starting one.** `/chats` itself — **Chats** at the top of the list, or **+** — is the landing: a composer whose first message becomes a new chat, suggestions that show what the app does — a classic network fetched from the web and explored in Unigraph, who influenced whom from Wikidata, a field's citation map from OpenAlex, three documents linked by the ideas they share (each opening as a tab of its own), the busiest air routes on the globe, the tallest buildings on a map with a note and a chart — each a title and a line on its card, and the whole request, sources named, in the composer when you choose it (with a project open, its own two come first: its most connected entities in Unigraph, a brief on what it holds), your **Recent chats** as cards — each with the last thing the assistant said, when, and icons for what it made — and **Recently made**: the documents, diagrams, maps and scenes chats made last, each opening beside its chat.

**A chat.** In the middle, the conversation — the same chat the assistant panel shows, full width, with the same composer as the landing; its settings and transcript download are in the header, and a double-click on the title renames it. Opening an earlier chat continues it, as **Resume** does; an imported one is shown to read.

**Its artifacts.** Everything the assistant made or changed in the chat — the documents it wrote, the diagrams it drew, the maps and places it laid out, the scenes it saved, the entities it created or edited — is listed under **Artifacts** in the header, newest first, with **Graph of this chat** (Unigraph on the chat's artifacts alone) when there are several. Files you attached to a message are there too: the chat is how they came into the project. Reading tools make nothing: a chat that only searched and looked has no artifacts. Places, paths and areas the assistant puts on a map are the map's — the map is the artifact, not one per pin. The panel that shows them is not there until it is needed: it slides in from the right when there is an artifact to show and slides away again when you close its last tab. **What the assistant makes opens there as it is made** — a new document, image, diagram, map, dataset, chart, script or entity arrives as a tab in front, the chat staying where it is — so you see it without asking; what it only changed waits under **Artifacts**, and **Artifacts**, a tool card's **Show**, or asking the assistant to show one open any of them again. (Away from the Chats page the same thing takes you to the new thing's own page, with the chat in the side panel. Asked to make something quietly — one of many, say — the assistant passes `open: false` and nothing moves.) Drag its left edge to make it wider; the button beside **Artifacts** hides and shows it. Each artifact is a tab, in the Workstation's tabs without its splits: a document in its editor, a diagram in its workbench, a map on its map, anything else in its detail view — the entity's own form first, its fields, links and annotations a tab away, and the expand button opens its full page as another tab — and a scene in **Unigraph** itself. Artifacts are heavy views — a graph engine, a map, a diagram, each with its own GPU context — so the panel keeps only the tab in front and the one before it running (the rest reload when you come back to them) and holds at most eight tabs: opening a ninth closes the one opened longest ago; anything closed is still under **Artifacts**.

While the Chats page is open the assistant panel steps aside — the page is the chat — and comes back as it was when you leave. When the assistant is the one taking you elsewhere — a tool opens a page, or you follow a link in its answer — the panel opens there with the same chat, so the conversation comes along.

The list of artifacts is part of the chat's record (`artifacts` on the conversation entity, each with the tool that last touched it and when), kept whole even though the record cuts tool results short, so a chat reopened next month still knows what it made. Over MCP, `chat {action:"artifacts", id?}` lists them with where each opens, and `chat {action:"show", id, artifact?}` opens the Chats page on a chat with that artifact — or any other entity — in the panel. On the Chats page the assistant is told it is there (a `chats_page` line in its context, with what the panel shows), so "open the map over there" puts the map in the panel rather than taking you to another page, and what its tools create lands in the panel rather than on another page. `/artifact/<id>` is the artifact view on its own, as a page or a Workstation tab.

## Voice

Voice control drives the assistant without its panel open. Turn it on with **⌘⇧U**, the microphone in the assistant's composer, or *Talk to the assistant* in ⌘K; a pill at the bottom of the page shows what is being heard, thought about or said, and a click on its microphone (or ⌘⇧U again) turns it off. The browser asks for the microphone once. Listening is continuous, and a command is as long as you keep talking: the recogniser finalises a phrase at every breath, and those phrases are joined into one command that is sent when you stop for the pause set in the assistant's settings (**Dictation ends after**, 1 s by default — shorter is snappier, longer leaves room to think mid-sentence; the pill says *Dictating* and shows the text growing) or when you end it yourself with **"send it"** or **"that's all"**. The command goes to the assistant as a message with the usual `<app_context>`, so "filter the graph to people around Ada" and "what am I looking at" work as they do typed, and the reply is read aloud **as it streams in** — each sentence goes to the speaker the moment it is complete, so the reading starts while the rest is still being written — the assistant is told voice is on and keeps to a few plain sentences. Anything the microphone hears that is the app's own voice coming back is dropped, not sent. The panel need not be open for any of this; open it (**⌘J**) to read the same transcript. Chrome and Safari can listen and speak; a browser without speech recognition shows the pill only for the error.

**Questions come by voice.** When the assistant needs a decision — a confirmation before it deletes something, reads a site it has not read yet, or changes a setting, or a question with options (`ask_user`) — the panel opens and the question is **docked above the composer** with a pulsing *Waiting for your answer* marker (it moves into the transcript once answered), and it is read aloud with the options — after whatever reply is still being read, never over it — ending with *choose in the assistant*. Answer either way: click, or say it — *yes* / *no* for a confirmation, an option by name, or by position ("the second one", "two", "the last one"); *none of those* declines. A chat answered by Claude Code puts its questions in the same place — the tool calls of that chat's `claude -p` are routed to the tab that started it, whichever tab is in front, and its `ask_user` and delete confirmations become cards in this panel; questions from Claude Code driving the tab from a terminal show as a dialog instead, spoken the same way. A phrase that is not an answer while a question is waiting gets the options repeated. A confirmation's button says what yes does — **Delete** or **Discard** in red when something is lost, **Allow** to let the assistant read a site, **Download**, **Turn off**, **Save and go on** — beside **Cancel**. The card itself is orange — something to be careful with — and red only when something is lost, and it keeps its colour once answered, as the record of what you allowed; typing *yes* or *no* (or the button's word) in the composer and pressing return answers it too.

**Automatic by default.** Both the listener and the speaker are set to *Automatic*: OpenAI whenever it can be reached, the browser's own recogniser and voice otherwise. OpenAI is reached with a key of your own in the settings, sent straight from the browser to OpenAI. **Running locally**, it is also the `OPENAI_API_KEY` in `.env.local`: the dev server serves `/api/openai` to its own page, so voice uses OpenAI with nothing else to set up. Your own key takes precedence. The settings say which way *Automatic* resolves right now.

**Who listens** is chosen in the assistant's settings under **Voice**. *Browser recognition* is Chrome's own (free, streams words as you speak, finalises at every breath; it hears names and long sentences poorly). It is not on your machine: Chrome sends the microphone's audio to Google, Safari to Apple — so with **Third-party services** off it runs only where the browser can recognise on the device (Chrome's on-device speech, once its language pack is installed), and otherwise says so and stops. *OpenAI transcription* records each command from the microphone until you stop talking for the dictation pause — the pill says *Dictating* with a ring that swells with your voice, then *Transcribing* — and sends that one clip to `gpt-4o-mini-transcribe` ($0.003 a minute; `gpt-4o-transcribe` is the option for hard audio), with the app's vocabulary and the names on screen (the project, the open document, the selected nodes) as a hint, so a whole command of any length comes back as one accurate sentence. A key entered here is stored in this browser only, sent straight to OpenAI, and takes precedence over the one in `.env.local`. A blip shorter than a word is ignored; a monologue past ten minutes is sent in parts. The transcriber is told the product's name and spelling — *Aegraph*, not "a graph" — and the assistant reads the usual mishearings (Agraph, AE graph) as the product.

**The voice that reads back** is chosen in the assistant's settings under **Voice**. *Browser voice* picks the best voice installed for your language — premium and enhanced voices, Siri's, or Chrome's Google voices, never the compact default or a novelty one — and lets you pick another. Chrome's Google voices and Edge's online ones read by sending the text to Google or Microsoft; with **Third-party services** off only a voice on the device reads, whichever you picked; on a Mac the good ones are downloaded in System Settings › Accessibility › Spoken Content. *OpenAI neural voice* reads replies through OpenAI's speech API (`gpt-4o-mini-tts`, eleven voices) — with your own key, or locally the key in `.env.local`; the audio is played as it streams in, so speech starts a few hundred milliseconds after the reply, and a failed request falls back to the browser voice and says so. The microphone stays open, muted, while the app speaks, so the next command can start the moment it stops. **Test the voice** reads a sample.

A few phrases are for the app rather than the assistant: **stop** cuts the speaker and the current turn, **stop listening** turns voice off, **open the assistant** / **close the assistant**, **new chat**. Voice is remembered per tab: left on, it comes back on when the app loads.

Over MCP the same is `voice` — `say` reads text aloud, `listen` / `stop` turn voice control on and off, `hush` stops speaking, `status` reports the state — and `ask_user` puts a question with options to the user (a card in the assistant, a dialog when the call comes over the bridge), spoken when voice is on.

### Connecting the assistant

The assistant answers in one of two ways, chosen in its settings (the gear in the panel's header):

- **Claude Code over the bridge** — your own Claude Code, on your subscription, with the app's tools ([below](/docs/assistant#chatting-with-claude-code-from-the-app)). **Running locally** (localhost, 127.0.0.1) it is the only way: the Claude API is never called from this machine, whatever key is present.
- **Your own Anthropic API key** — on a deployed copy of the app, paste a key into the settings. It is kept in this browser only and sent straight from the browser to the Claude API; nothing sits in between, and the model and effort are yours to choose.

With neither, the panel and the Chats page — its landing as well as an open chat — open on the settings: locally they say to connect Claude Code, elsewhere to add your key or connect Claude Code. Closed, they are a click away: the gear in the panel's or the chat's header, or **Settings** beside the Chats composer. There are no accounts: nothing to sign in to, and nothing paid for by anyone but you.

**Voice through OpenAI** works the same way: with an OpenAI key of your own in the settings, or locally with `OPENAI_API_KEY` in `.env.local`, which the dev server uses for its `/api/openai` (see `.env.example`). Without either, voice uses the browser's own recogniser and voice.

## The bridge

`mcp/server.mjs` is an MCP server (stdio) that hosts a local WebSocket; the running app tab connects to it, sends its tool manifest, and executes every call in the browser. The server holds no state — the tools are always exactly what the app exposes.

**Getting it running is one command.** The sidebar's **Claude Code** dialog shows it with a Copy button. On the deployed site it is running the app on your machine — `git clone <this edition's repository> && cd <it> && npm install && npm run dev`, then `http://localhost:5173`; Claude Code connects to the app running there, not to the site. On that local app the dialog's command is `claude` in the checkout: Claude Code starts the bridge from the project's `.mcp.json` (it asks once to approve the `aegraph` server) and the tab connects. The repository is the edition's own (`src/app/edition.ts`).

```sh
npm run dev       # the app, http://localhost:5173
claude            # in this repo; .mcp.json registers the "aegraph" server
```

The tab does not have to be the dev server: a deployed copy of the app connects to the same local bridge, since the connection goes *out* from the page to `127.0.0.1` — once the bridge trusts that site. By default that is **aegraph.sh**, where this edition is published; set `AEGRAPH_HOSTED_ORIGIN` to your own deployment's origin (`https://your.site`) where Claude Code runs, or empty to trust only this machine's pages. Chrome gates that behind its **Local Network Access** permission — the first time, it asks whether the site may connect to devices on your local network; allow it (it is remembered per site). If the bridge stays on *connecting…* on a deployed site, check that permission in the site's settings (the lock icon → Site settings → Local network access). Headless runs cannot answer the prompt: `mcp/drive.mjs` takes `CHROME_FLAGS=--disable-features=LocalNetworkAccessChecks` for that.

`aegraph_bridge_status` reports whether a tab is connected. Calls that delete, reach another site or change a setting pause on a confirmation dialog in the app, its button naming what yes does. With several tabs open, calls go to the tab you last brought to the front (a tab that connects in the background does not take over) — among the tabs from the site the first tab came from: a page from another local origin (another dev server, a tool you run) can connect but never takes the calls, and `aegraph_bridge_status` lists it as not routed. With `AEGRAPH_BRIDGE_TOKEN` set, every tab that has the token is routed to. The bridge itself fetches nothing: a picture reaches Claude Code only as pixels the tab sends, after asking you. Environment: `AEGRAPH_BRIDGE_PORT` (default 8787, bound to 127.0.0.1), `AEGRAPH_BRIDGE_TOKEN` (optional shared secret), `AEGRAPH_BRIDGE_TIMEOUT_MS`.

### Two apps, two Claude Code sessions

By default every session's bridge takes the first free port from 8787 up, and every tab connects to all ten ports from its bridge URL (8787–8796). So all sessions reach all tabs, and each call goes to the tab in front. To give each session an app of its own, give each pair its own range of ports:

```sh
npm run dev                            # app A, bridge URL left at ws://127.0.0.1:8787
npx vite --port 5210 --strictPort      # app B
claude                                 # session A: bridge on 8787
AEGRAPH_BRIDGE_PORT=8797 claude        # session B: bridge on 8797
```

In app B's tab, set the bridge URL in the bridge settings to `ws://127.0.0.1:8797` (Enter to apply). B then connects to 8797–8806 only and A to 8787–8796, so neither session sees the other's tab. The setting is remembered per origin, which is why the second app runs on its own port. For the same reason the two apps do not share a Library or projects. Chats started from an app's panel start their bridge within that app's range, so they stay with it too. A session started without the variable lands in A's range. `aegraph_bridge_status` in each session shows which tab it has.

### Chatting with Claude Code from the app

The bridge works the other way round too: with it connected and no API key in the browser, the assistant panel sends its messages to Claude Code (the header says **Claude Code**; on a deployed copy, a key set alongside can be overridden with *Answer through Claude Code* in the panel's settings). **Running locally (localhost, 127.0.0.1) the chat is Claude Code only**: the Claude API is never called from this machine, whatever key is present, and without the bridge the panel says to connect it. Each message runs one `claude -p` turn on your subscription, in an empty folder of its own (under your user's cache, `aegraph/chat`) rather than in the repository, with its own copy of the bridge so the turn has the app's tools; the next message resumes the same Claude Code session — the session id is kept from the turn's first event, and the transcript is saved as it changes, so a reload (even mid-turn) comes back to the same chat and the same session — and **New chat** starts a fresh one. The turn is over for you at Claude Code's `result`; the process is given a few seconds to exit and then put down (`AEGRAPH_CLAUDE_LINGER_MS`, default 5000), so a lingering shutdown never holds the next message. The turn's events stream into the panel as they happen — text, tool calls and their results — like the API path. A tool call shows as soon as the model starts it, not when it has finished writing it: a document the assistant is writing into `create_document` is most of a turn's time, so its card goes up at once with the document's title and counts the words as they arrive, and "Thinking…" counts the seconds before that. **Model and effort** for Claude Code turns are their own, in the assistant's settings (locally they are the only ones; with a key they sit under the API's): Sonnet 5 at medium effort by default — several times faster than Opus at writing, and thinking less before it starts — with Opus 5.5 and high effort a choice away for work that wants the care. Each turn runs `claude -p --model <it> --effort <it>`; a spoken turn always runs at low effort.

A turn has **the app's tools and nothing else**: no shell, no reading or editing files, no web fetch, no sub-agents. What the panel sends — your selection, the open document, the assistant's notes — and what the tools return is workspace data, and some of it may have been written by someone else to steer a model; with the built-in tools gone, nothing it says can become a command on your machine. The turn also gets only the environment Claude Code needs to sign in and reach its API (or Bedrock / Vertex, or a proxy), none of your terminal's other secrets.

**It is not your Claude Code.** A chat from the app never joins, resumes or reads a Claude Code session you have open in a terminal, and nothing it does reaches one. Each turn is its own `claude -p` process, started by the bridge and gone when it has answered; it resumes only the chat's own session, which Claude Code files under the chat folder, so it never appears among your project's sessions (`claude --resume` in the repository). It reads your `CLAUDE.md` (the one in `~/.claude`) and keeps Claude Code's auto-memory like any session of yours — its own memory, filed under the chat folder, not your repository's. It does not run your settings file (`--setting-sources project,local`, and the chat folder has no project settings): your hooks would fire on every chat turn and your permission rules would widen the turn's. And it does not carry the identity of the session that started the bridge (its session id, project directory and messaging socket are not passed on). What it shares with your terminal is your sign-in, your `CLAUDE.md` and your subscription's usage. Your session in the terminal sees the app only if it calls the app's tools itself. The app's tools are pre-allowed (the app confirms the destructive ones itself); anything else Claude Code asks for is put to you in the app first (**Claude Code asks for permission**), whole — a request too long to show in full is declined without asking — with **Cancel** focused. `Stop` ends the turn; a tab runs three turns at once at most. Environment: `AEGRAPH_CLAUDE_BIN` (the `claude` to run, default from `PATH`), `AEGRAPH_CLAUDE_ARGS` (extra arguments, e.g. `--model claude-sonnet-5`; a flag that would widen the turn's permissions — `--permission-mode`, `--allowedTools`, `--tools`, `--add-dir`, `--settings`, `--dangerously-skip-permissions` and the like — is ignored, and the bridge says so).

Every tool result the bridge hands to Claude Code — to a turn from the panel and to a Claude Code session in your terminal alike — is wrapped in `<untrusted_data tool="…">…</untrusted_data>`, and the bridge's instructions tell the model that nothing inside it is an instruction. A closing tag inside the data is broken before it is wrapped, so the data cannot end the envelope early. A remote image a result names is fetched by the bridge only over https from a public address — never the loopback, the local network or a cloud metadata endpoint — with a 20 MB cap and a 15-second limit. The bridge server can also run on its own, with no Claude Code session in a terminal: `npm run mcp`.

Two things to know when driving the explorer over the bridge:

- Tool results are applied on the app's next render; a tool reports what it computed rather than re-reading state immediately afterwards.
- `get_app_context` includes `recentErrors` — the last uncaught errors in the tab — so a failed mount can be diagnosed without opening devtools.
- Calls are independent: each carries its own id, the tab runs them as they arrive, and the server matches replies by id. A call the client gives up on (Claude Code waits 60 s) does not hold up the ones behind it; the tab finishes it anyway and its late reply is dropped. If every call is timing out, the tab itself is stuck — a synchronous computation on its main thread, a confirmation dialog nobody answered, or a machine out of memory — not the bridge.

## Headless: the engine with no browser

The UI is one client of a logical engine — an entity store, an ontology, filters, layouts, metrics, projects, constraints — and none of that needs a DOM. `src/headless` hosts that engine in Node and exposes the app's own tools over stdio MCP, so a project can be created and managed with no tab open at all:

```sh
npm run headless -- ~/work.ae.json                       # build + run on a workspace file
claude mcp add aegraph-headless -- node /path/to/aegraph-ui-toolkit/dist-headless/aegraph-headless.mjs ~/work.ae.json
```

**One instance, several clients.** Given a port instead of stdio the engine stays up and each client connects over MCP's streamable HTTP transport — Claude Code in a terminal, a script, another session — all driving the same workspace:

```sh
node dist-headless/aegraph-headless.mjs ~/work.ae.json --port 8788
claude mcp add --transport http aegraph-headless http://127.0.0.1:8788/mcp
```

It listens on the loopback only: the engine reads and writes this machine's files, which have no business on the network. And one process owns a workspace — it autosaves, so two would overwrite each other's idea of it — which a lock beside the file states: a second process is turned away, told which pid holds it, and takes over silently when that process is gone (`--force` takes it regardless).

One file is the whole state. It is read at boot (`.ae.json`, or gzipped `.ae.json.gz`), written back a quarter-second after every change that touches the data — `workspace_save` writes it on demand, `--no-autosave` leaves it to that call alone — and the project that was open is reopened next time. The write goes through a temporary file and a rename, so a crash mid-write cannot lose the workspace.

**The tools are the app's tools**, the same files the assistant and the bridge load in a tab: entities and relationships, documents, projects and their history (commit, changes, restore), the ontology (`define_entity_type`, `table_layout`, `update_tag`), constraints, Insights (`analyze`), scripts, datasets, charts, maps, diagrams, memory, `validate_ae`. What is not there is what a browser owns — the explorer's canvas and camera, the globe, the media players, the workstation, voice — because "it is now on screen" means nothing here.

Four tools exist only headless, for the state a caller cannot see for itself:

- `workspace_status` — the file, the counts, the open project, whether anything is unsaved, where commit content is kept, and the projects in the workspace. The equivalent of looking at the window; call it first.
- `workspace_save` / `workspace_reload` — write now; or re-read the file after something else changed it (a generator, an editor).
- `open_project` — scope the engine to a project, or to the whole Library. Everything afterwards sees that scope, exactly as the app does with a project open.
- `import_file` / `export_file` — the Projects dialog as a path. A project bundle is opened as its project; anything else is merged into the open project. Formats are the app's own, gzip included.

And the graph, computed rather than drawn:

- `graph_slice` — what a filter selects: counts, the breakdown by type and relationship type, components, the highest-degree nodes.
- `graph_metrics` — the analytics of [Analysis](/docs/analysis) over that slice (degree, PageRank, betweenness, communities…), with the top nodes per metric; `write: true` puts the values on the entities, `save` keeps the run as an analysis entity.
- `graph_layout` — any layout in the catalogue, reported rather than rendered: how long it took, the extent it covers, and for `tree` the hierarchy it found (roots, depth, the cross-links it could not draw). Enough to tell a real hierarchy from a mesh on a plane before anyone opens it. `write: true` stores the positions as `data.x/y/z`, so the app opens the view exactly as computed here.
- `graph_scene` — a whole [Unigraph](/docs/explorer) scene composed rather than captured: **data + filter + layout + style**, plus the view metadata a scene carries (camera, labels, edges, legend, which panel is open, the selection). Each part is saved as the entity the explorer saves — a `filter`, a `layout` holding the computed positions, a `rendering` (the style, described in the same channels as `graph_style`), an `analysis` when metrics are asked for — and the scene binds them, so `/unigraph/2d?scene=<id>` opens exactly the picture that was composed. `filter_id` / `layout_id` / `style_id` reuse parts across scenes; `export_data` pins the scene to an exported view (its slice and metric values) as its data stage. In two dimensions a scene with no camera is framed by the app on its own positions when it lands; in three the scene carries the orbit camera, which is absolute. With no canvas to capture, the scene's card picture on the Scenes page is drawn from the slice at its computed positions (`data.preview`, an SVG) — as `plot {action: "save"}` draws a chart's.

**Scripts run here too.** The JavaScript sandbox is QuickJS compiled to WebAssembly, which Node runs as happily as a browser: `script {action:"run", code}` — or `id`, a saved script — evaluates in this process instead of a worker, over the same dataset snapshot, with the same helpers and the same time and memory caps. What a script returns is what it returns in the app: a table, a figure, a layout, a style, a filter's ids. Python and Visual scripts are not headless — they need Pyodide and an iframe. Charts are `plot` as usual: `preview` computes the points, `save` keeps the chart entity.

The filter and layout vocabularies are `core/graph`'s own, so a scene computed headless and one built in the app come from the same code. On a 6,000-entity / 14,000-relationship workspace, booting and reading the file takes about 300 ms, `graph_slice` 18 ms, degree + PageRank + Louvain 80 ms, a tree layout 45 ms, and `analyze` 140 ms.

**History is on disk too.** Commit content lives in its own IndexedDB database in the browser; headless it is a folder beside the workspace (`<workspace>.history/<commit>.json.gz`, one gzipped file per commit, read only when a diff is viewed or a commit restored), so `project_commit` in one process and `project_restore` in the next work the way they do across reloads in the app.

`npm run smoke:headless` is the end-to-end check with no browser anywhere: a project created over MCP, entities, relationships and a document added, a type defined, the graph filtered, analysed and laid out, the project committed and exported, the workspace saved — then a second process on the same file, which must find everything where the first left it, restore that commit from disk, and read the exported bundle back in as a project.

### Headless save recovery and destructive file operations

`workspace_status` reports `unsaved` and `saveError`. A failed autosave keeps the engine running with the unsaved workspace in memory; correct the filesystem problem and call `workspace_save` to retry before stopping it.

With destructive operations disabled (the default over HTTP), `workspace_reload` refuses to discard unsaved work, `import_file` refuses replacement and collisions with existing entity IDs, and `export_file` creates new files only. Enable destructive operations at startup with `--yes` only for a trusted client.

With no one to ask, a tool that would ask before reaching a site it was handed — an image, a bundle, a page — is declined unless the engine was started with `--allow-network` (off by default, over stdio and over a port alike), and then reaches public addresses only.

## Recipes

**Start small.** `graph_state {brief: true}` is the essentials in about a kilobyte (mode, what the filter/layout/style are, counts, loaded part ids, selection, dataset, load and gate, physics and layout status, saved-item counts); add sections by name with `include: ['rendering', 'valueRefs', 'saved', …]`. The bare call returns everything — style rules, palettes, algorithms, every value ref and saved item — which is ten times the size and rarely all needed in one turn.

**Look, then act.** `graph_query` with a selector and a list of values returns rows; `graph_positions {action:'place'}`, `graph_style`, `graph_select` and `graph_selection_action` accept the same selector.

**Filter by an analysis result.** `graph_metrics {metrics:['pagerank']}` → `graph_project {action:'export', name:'Ranked'}` → `graph_project {action:'load', id}` → `graph_filter {fields:[{path:'data.pagerank', op:'gte', value:0.01}]}`. See [The pipeline](/docs/pipeline#iterating-with-projects).

**A heatmap grid of documents** — the example in [Position layouts](/docs/positions#example).

**"Open the Entities table with everything about architecture."** `open_entities {title:'Architecture', query:'system architecture: services, infrastructure, data stores and how they connect'}` — the tool reads the vocabulary in use (every type and tag with its label, description, examples, usual tags and links) and ranks it by meaning, then opens the union of what scored as a new tab of that name, relationships among the picked entities included. Three engines, chosen in this order: **model** — Claude reads the vocabulary, using the API key in the assistant settings; **local** — sentence embeddings in the browser (all-MiniLM-L6-v2, about 23 MB, downloaded once after you say yes in the app and cached by the browser; nothing is fetched until a semantic search is actually run), which also reads the entities themselves so a document about the phrase counts whatever its type; **lexical** — word overlap, when neither is available, and the reply says so. Similarity scores are relative, so the local engine keeps what is within 65% of the best match (75% for entities) unless you pass `threshold`; a descriptive phrase ranks far better than a single word. `dry_run:true` shows the ranking first; `engine` forces one; explicit `ids`, `match`/`matches` (types / tags / text) and `related_to:[ids]` (one hop, links included) are unioned in; `category` lands on a section.

**Save the whole arrangement.** `graph_save {kind:'scene', name}` saves unsaved filter/layout/style parts and one scene entity; `open {page:'/unigraph/2d?scene=<id>'}` reopens it.

**"Create a graph of just the conversation segments about philosophy and all their associations, and save it as a view I can reopen."** Find the vocabulary first: `open_entities {title:'Philosophy', query:'philosophy', dry_run:true}` ranks the tags in use (`domain:philosophy`, `topic:philosophy`, `topic:ancient-philosophy`…). Build the neighbourhood in one filter: `graph_filter {replace:true, roots_match:{types:['segment'], tags:[…those tags]}, depth:1}` — every matching segment is a root and everything one hop around it comes along (conversations, topics, clusters, named entities and the links between them); the reply gives the counts, and a view past the [view budget](/docs/explorer#large-graphs) says so. Then `graph_save {kind:'scene', name:'Philosophy segments and their associations'}`: the scene is an entity (Entities → Graph scenes) that `open {page:'/unigraph/2d?scene=<id>'}`, its row under Entities → Graph, or a workstation tab reopens with the same filter, layout and style — in 2D; loading it in the 3D explorer shows the same picture there.

**"Load all the trees into Unigraph 2D with fixed positions, colour coded by genus."** Three calls, on the *Street trees of Toronto* project or any dataset of located things: `graph_filter {replace:true, types:['tree'], mode:'2d', accept_large:true}` puts every tree in the view (688,335 nodes is within the engine's budget; `accept_large` skips the gate); `graph_positions {action:'place', selector:{types:['tree']}, spec:{arrangement:'geo'}}` puts each where it stands — Web Mercator of its latitude and longitude, north up, the city's shape kept — and holds the positions (fixed: no simulation moves them; `graph_save {kind:'layout'}` keeps them as a layout); `graph_style {channels:[{scope:'nodes', by:'all', channel:'color', mode:'partition', attr:{kind:'tag', prefix:'genus:'}}]}` colours by the `genus:` tag namespace, and the legend lists the genera with their counts. Any tag namespace or `data.<key>` colours the same way.

**"Put all the tree entities into a dataset."** `dataset {action:'from_entities', selector:{types:['tree']}, name:'All the trees'}` — the rows are the entities the selector names over the whole dataset (types, tags, text, field predicates), the columns their fields: id, label, type, tags, then every property the type declares, coordinates included; `columns:['label','data.dbh']` keeps just those. No script runs, so any number of entities; the table opens on the Datasets page (`open: false` to stay where you are). The Entities table's Export menu does the same for the rows it shows (*Keep as a dataset*).
