# Projects

## One Library, many projects

Everything the app knows lives once, in the **Library** — the store persisted in this browser. A **project** is a named scope over it: the entities marked with the project, plus the scope of any projects it *includes*. An entity can be in any number of projects and is never copied; a project's presentation state — layouts, positions, scenes, renderings, workstations, diagrams, plots — is created inside the project and so belongs to it.

The control under the logo in the sidebar says what you are looking at. Pick a project and every page and every tool is scoped to it: the tables, the media libraries, the graph explorer's dataset, search, counts. Pick **Library** to see everything.

## What goes into a project

- **Created while it is open.** Annotate a document, save a scene, arrange a workstation — the new entities are marked with the open project. Nothing to do.
- **Opened as a demo.** The Projects dialog's **Demos** tab shows the demo projects the deployment ships — bundles put under `/demos/` at build time, by default the copies aegraph.dev publishes (a checkout of the private `aegraph-ui-demos` repo, where the demos are built, takes precedence); the app carries no projects of its own — as cards with their pictures, each opened with a click; `load_dataset` lists them with their ids and opens them the same way. A demo is a bundle, so it becomes a project of its own and reloads in place after an update; a card whose demo is already in your Library says *In your Library*, and opening it again reads the demo afresh. When that brings a newer version — an entity of the demo created or updated — the project opens on the demo's own screen again, even when it is the project you are in: its workstation with fresh tabs, each scene loaded anew from its new parts (a Unigraph tab keeps its own copy of a scene's filter, layout and style, so a tab kept from before would go on drawing the old version). Opening the same version again changes nothing, and leaves the screen as you arranged it. A demo of a million or more entities and relationships is marked **Heavy** and says on its card that it pushes the browser to its limits — about how much memory it takes once open, to keep a scene's filter on in Unigraph (clearing it asks before drawing everything, see [Large graphs](/docs/explorer#large-graphs)), and that it is not for phones. The project that opens remembers where it came from (`data.demo`, the bundle's path), so the dialog keeps it on the Demos tab rather than among your own, and `project_list` reports it with `demo: true`. On a dev server beside a checkout of the demos repo, the cards read that checkout as it is on disk, so a demo just rebuilt by its generator is what the card opens.
- **Shared as a link.** A demo opens from a link: the site's address with `?demo=<id>` — and `&scene=<scene>` to land on one of its scenes, by its id or the short name after `scene:<id>:` (`?demo=kestrel-story&scene=from-information-to-decks`). Whoever follows it gets the demo as a project of its own — updated in place if they have it — on that scene in Unigraph, a workstation of one pane; without a scene, on the demo's own first screen. It works on a first visit and any other, and the default project does not open over it. In a demo project, the scene menu's **Copy link to this scene** makes one; `load_dataset` lists each demo's link. The id is looked up only in the site's own demo catalog, so a link cannot make the app fetch anything else.
- **Loaded while it is open.** The dialog's Import and Examples tabs (and `load_dataset` with a dataset on this machine) merge into the Library and mark what they load with the open project. Import a CSV into one project and a ChatGPT export into another; switch between them; neither is wiped.
- **Added explicitly.** Select rows in a table and use **Projects ▾**, or right-click a row, or the *Projects* row in the inspector: *Add to …* / *Remove from …*. Relationships between the added entities and the project's members come along. Removing never deletes.
- **Included.** A project can include other projects (`includes`); their scope is part of its scope without re-marking anything. Cycles are refused.
- **Types.** A type definition is an entity like any other, so a project holds the types made in it or brought in by its bundle. Two more show whenever they apply: the definition of every type in use in the project, and definitions that belong to no project — vocabulary made in the Library is shared. A demo's types stay with the demo; a fresh project starts with the built-in types and the Library's own.

Switching projects also swaps the pages' remembered state — the explorer's filter, layout, held positions and camera; the workstation arrangement; the Scenes page's last scene; the plot draft — so two projects feel like two windows. One part of that does not currently hold: a Unigraph tab keeps its own explorer session, under a key the swap does not name, so its filter, layout and held positions stay as they are across a switch (the camera, and every other page here, do swap).

## Your projects

The Projects dialog (*Open project…* in the sidebar's project menu, or `/new`) opens on **Your projects**: every project in the Library that is not a demo, as cards — the newest graph scene's picture when the project has one, else its own colour — with the name, description, size and when it last changed. A click opens one; the open one is marked *Open now*. **New project** and **Open a file…** are at the top, a bundle dropped anywhere on the tab opens too, and on a dev server the bundles this machine serves (`AEGRAPH_LOCAL_DEMOS`) are listed under *On this machine*. With none of your own yet, the tab says *Your projects will be here* and offers the same ways in, plus the demos. *Start fresh*, at the foot of this tab and of Demos, empties this browser before what you open next — asked once more first; off, what you open is added beside what is here. The [Projects](/projects) page is where projects are managed: saved, deleted, versioned.

## Bundles

**Save project…** writes `<name>.ae.json` (an aegraph document — see [File format](/docs/spec) — with `project` and `state` keys): the project's scope, the relationships among it, everything its presentation entities reference — a scene's filter, layout, rendering and analysis, a projection's diagram, a slide's deck, compose and beats, a block's children and items, anything named under a key ending in `Id` — the type definitions and tag colours in use, the project entity, and the screen state (route, explorer, workstation) to reopen it on the same screen. Only those references are followed: a dataset cell or a note that happens to hold another entity's id does not bring that entity, from whatever project, into the file. What the references reach outside the project is counted in the save's result (`outside`). The bundle carries the project's **assistant chats** and the assistant's **memory** document for it, as it carries any other entity of the project. **Open project…** (the Projects page, the sidebar's project menu, or `/open?url=…`) merges it into the Library by id — newer wins, nothing is wiped — makes it a project, and opens it where it was saved. A plain `aegraph/v1` document opens the same way and becomes a project named after the file.

A bundle changes only what is its own. Its new entities join its project and no other — a file cannot put anything into one of your projects. Entities of its project already in the Library (a demo opened again) are updated when the file's copy is newer. Anything else in the Library that the file also holds — an entity in no project, or in your other projects — is left as it is and counted, and the file's other projects are never written. A bundle never brings `includes`: an opened project includes nothing it did not include already. A type definition or tag colour you already have differently is kept unless you agree to the file's; a date later than now is brought back to now, so a file cannot stay newer than your next edit; and its constraints arrive disabled ([Constraints](/docs/constraints)). A file with a value nested more than 64 levels deep is refused. Over MCP, `project_open_bundle` asks before it opens a bundle that would replace entities you have — saying how many and naming a few — and refuses one that would replace the assistant's own memory.

## Publishing a project

**Publish as web page** (on the project's page, or `project_publish` over MCP) writes one self-contained, read-only HTML file — `<name>.html` — that anyone can open without the app: the overview (types with counts, relationship types, the top tags), every saved graph scene drawn as an SVG through the same filter, saved positions and style rules the explorer uses (styles that read metrics — colour by community, size by PageRank — get them computed), Unigraph's current view when it is open on the project, every chart as a picture, the latest findings with the claims and named communities kept from them, the documents rendered, and a searchable table of every entity that opens to show its relationships. It leaves out your chats with the assistant and the assistant's memory document — your conversation, not the project's content — unless `project_publish` is asked to include them. Findings, claims and chart captions link into the table. The page is a snapshot: it does not change when the project does. Very large projects list the first 20,000 entities and say so.

## Where projects live

Everything — the Library and every project — is in the **browser's own storage** for this origin (IndexedDB database `aegraph`): saved as you work, never on the network. A project opened from an `.aeb` is kept there as the file it came in, as long as nothing in it was already in the Library — saving it takes no time however big it is — and what you change after goes beside it. The browser keeps that under its profile (Chrome on a Mac: `~/Library/Application Support/Google/Chrome/<Profile>/IndexedDB/…`), but those are the browser's files, not ones to open or copy.

**This browser holds the only copy.** There is no server copy and no sync: another browser, another profile or another machine starts empty, and clearing this site's data (the browser's *Clear browsing data*, a private window closing, a profile deleted) deletes the workspace with it. At startup the app asks the browser to keep its storage **persistent**, so it is not evicted when the disk runs short — Chrome and Edge decide silently, Firefox asks you once, Safari decides by its own rules — and **Where your projects live** on the Projects page says what the browser answered (*Kept*), with **Keep it** to ask again. Safari may also clear a site's storage after seven days of browsing without a visit to it (a site added to the Dock or the Home Screen is exempt). So treat the browser as a working copy and **bundles as the record**: save each project you care about with **Save project…** into a projects folder that is backed up or synced (below), or export it; a team shares work the same way, by passing bundles — a shared drive, a repository of their own, a message. A bundle carries the project and its screen state but not its version history: commits stay in this browser (see *Versions* below).

Saving is continuous and needs nothing from you: each change is queued and written in the background, a big import as pages of a few thousand entities. While writes are on their way, leaving the page — reloading, closing the tab — makes the browser ask first, and the reload the app makes to pick up a new version waits for them. When a write fails (the browser closed the database, its storage refused), it is not dropped: the app opens the database again and retries, and what still fails stays in memory, written with your next change. Meanwhile a notice at the foot of the screen says **Not saved to this browser**, with how many changes are waiting and a **Try again** button — reloading then would lose them. The Dashboard shows the same state, and `app_diagnostics` reports it as `saving`. Several tabs of the app share the one database and can write at the same time without overwriting each other.

If the workspace cannot be read at the start — the database held by another tab mid-upgrade, a storage fault — the app still opens, but it does not pretend: a notice that stays on screen says **Your workspace could not be read from this browser**, that nothing you do now will be saved, and offers **Reload**. What this browser has saved is left exactly as it was — nothing is put in its place (a first visit's sample data goes in only when there is no database at all), and nothing is written over it. Leaving the page after any change asks first, and the reload the app makes for a new version holds off.

A project you can *see* on disk is a **bundle** (`<name>.ae.json`). On the Projects page, **Where your projects live** shows the storage facts and lets you pick a **projects folder** (Chrome and Edge): from then on **Save project…** writes the bundle into that folder instead of Downloads, and the bundles in it are listed there to open. The folder is remembered; the browser asks once per session to allow access again. Without a folder (or in a browser without the File System Access API), Save project… downloads the file and *Open project…* loads it back. The sidebar project menu's **Where projects are stored…** goes straight there. Pick a folder you would keep any other document in — somewhere backed up, and not a source tree: a project full of real data committed to a repository by accident is hard to take back ([Privacy & security](/docs/privacy)).

## Save as new project

**Save as new project…** (the sidebar menu, or a project's page) makes a second project holding what the open one holds. The dialog is the review: name and description, where the copy opens, entity counts by category and type, relationship types, the tags in play, and what the source includes. Entities are referenced, not duplicated — a document, a scene or a workstation in both projects is one thing, and editing it from either changes it in both. The copy keeps the source's includes and home, gets the source's current screen state (explorer, positions, camera, workstation) so it opens looking the same, and becomes the open project. From the Library the same action snapshots everything (projects and type definitions aside) into a project.

## Versions: commits, unsaved changes, autosave

Everything a project holds is kept in the Library the moment it changes; closing the tab loses nothing. **Saving to the project** means something more: recording a *commit* — a named point in the project's history you can compare with and go back to, in the way a Git repository does. The difference between the last commit (HEAD) and what the project holds now is its **unsaved changes**.

A project's own pages carry this: under its title on the Projects page (or the sidebar project menu) are **Overview · Changes · History · Settings**.

- **Changes** (`/projects/<id>/changes`) lists what changed since the last commit, grouped *added / modified / removed*, one row per entity with its type and label (relationships as *A → B*), filterable by type. A row opens to its **property diff**: every changed property with its value before and after — `label`, `tags`, each `data.*` field walked into nested objects (`data.address.city`), relationship ends. A long text — a document's `data.content`, a transcript — is shown as a **line diff** with context folded; a picture (an image's `data.src`) side by side; a list of records — a conversation's messages, annotations, an Excalidraw diagram's elements — as the items added, removed and changed (matched by `id` when they have one); a DOT or Mermaid diagram's source as lines; any other data URL as its size. Type a message and **Commit**; **Revert** on a row puts that one entity back as committed (an added entity is taken out of the project, a removed one restored); **Discard all…** puts the whole project back at HEAD, for good. The sidebar's project control shows the number of unsaved changes, and the *Changes* tab carries it as a badge.
- **History** (`/projects/<id>/history`) is the commit log, newest first by day: message, who or *autosave*, when, and the counts `+added ~modified −removed`. A commit opens to the same diff view for what it changed, with *Parent* to walk back and **Restore this version…**: the project is made what it was after that commit — edits since undone, entities added since taken out (deleted only if they were in no other project), removed ones put back — and that state is recorded as a new commit (*Restore abc1234 — message*), so the history stays a straight line and the step can itself be undone.
- **Settings** (`/projects/<id>/settings`) holds the name, description and home route, and the **saving mode**: **Autosave** (the default) commits on its own once the project has been quiet for a while (30 s; adjustable) and when you leave the page, labelled *Autosave*; if an autosave cannot be written (the browser's storage refused it), a notice says so — the changes are still in the Library, just not yet in the project's history — and the next autosave tries again. **Commit by hand** lets changes accumulate until you commit them with a message. Either way you can commit by hand at any time. *Forget history…* deletes the commits and their content; the project is untouched — the same button, and the same question, stands at the top of the History page, which is where it is usually wanted.

What a commit compares is the *content* of the entities in the project's scope — type, label, description, tags, data, relationship ends, source — by a content hash per entity. Bookkeeping (`updatedAt`, last opened, which other projects an entity is in) is left out, so a re-import of identical data or adding an entity to a second project is not a change. Project entities and the commits themselves are never part of a tree. The Library itself (no project open) has no history: commits belong to projects.

Where it lives: each commit is a `project:commit` entity in the Library (message, parent, counts — visible under Entities › Project); its content — the entities added, modified and removed since the parent — is a record in a second IndexedDB database, `aegraph-history`, read only when a diff is viewed or a version restored, so a long history costs the Library no memory. When a project or a commit is deleted, its content goes too, at a later start — once it has been without its commit for a day, so a commit another tab of the app is writing at that moment never loses its content. History stays on this device: a bundle carries the project, not its commits (see the follow-ups for carrying history with a bundle).

Over MCP and in the assistant: `project_changes` (counts, the list, or full property diffs — long texts as changed-lines diffs), `project_commit`, `project_history` (the log, filtered by message, time — `since: "2h"`, an ISO date — and autosave; one commit's diff, narrowed to one entity, with `content` for the entity as it stood after that commit — a document's text at that point; one entity's own history, every commit that touched it; or `from`/`to` for everything that changed between two commits, `to: "working"` for the uncommitted state), `project_restore` (a commit, `discard: true`, or one `entity` — whenever unsaved changes would be lost, the user sees them in the app and chooses *Save them first* (a *Before restoring …* commit, so the step can be undone), *Discard them* or *Cancel*; over the bridge the question is a dialog in the tab, and the call waits for the answer; `unsaved: "save" | "discard"` carries an answer the user already gave), and `project_update` with `autosave` / `autosave_seconds`. Commits are named by id, short id, a unique prefix, `HEAD`, `HEAD~2`. The assistant's context carries the open project's version state on every message — HEAD, the unsaved counts, the saving mode — so "what did I change?" and "what did this say before?" need no lookup first. `project_list` reports each project's HEAD and saving mode.

## Deleting

Deleting a project removes it, its marks and its commits; the entities stay in the Library. The dialog also offers to delete the entities that were in no other project, with the count.

## Over MCP

`project_list`, `project_create` (with `from` for *save as new project*), `project_open`, `project_add`, `project_remove`, `project_update`, `project_delete`, `project_save`, `project_open_bundle`, `project_template`, `project_changes`, `project_commit`, `project_history`, `project_restore`, `load_dataset` and `delete_entities` — see the tool reference on the Assistant & MCP page. `get_app_context` reports the open project.

For a scripted check of all of this against a running dev server, `npm run smoke` drives a headless tab through the MCP bridge: project, load, relaunch, properties, bundle, reopen.

## Templates

A **project template** is the analytics for a *kind* of dataset — charts, scripts, graph scenes, a guide, the Analytics and Workstation arrangements — with none of the data. Applied to a project that holds that kind of data, it draws over it at once, and applying it again after the data is refreshed updates the pictures in place (its entities are the template's, prefixed with the project's id, so two projects can carry the same template).

The app ships the **Conversation atlas** template for a ChatGPT export run through the atlas pipeline, a separate, private tool that labels and clusters conversations: fourteen charts (the pace of conversations, subjects over time and a month × region grid, stakes and modes, the shape of the exchanges, models), eight scripts (top topics, domain × theme, topic emergence, intent mix, region timelines, length trend, hubs, what stood out), four graph scenes (regions and clusters, conversations by cluster, topics and domains, similar segments), and a guide. Every chart and script selects rows by type and reads the fields the pipeline always writes, so it works over anyone's export. To see an atlas without an export of your own, the Datasets page has one made the same way at a million entities: *A conversation atlas of WildChat*, 489,731 public ChatGPT conversations labelled and clustered by the pipeline, with its own charts and scripts sized to that scale.

To use it: the pipeline writes `conversation-atlas.ae.json`, a project bundle whose project names the template. **Open project…** (or `/open?url=…`, or `project_open_bundle` over MCP) opens it as a project and adds the template's pictures on that first open; opening a fresh run of the same bundle updates the data in place and leaves the pictures — yours by then — alone. A bundle can name any shipped template the same way (`data.template` on its project entity). For data that arrived some other way, **Project templates** in the dialog's Examples tab does the same by hand: *Apply* adds the analytics to the open project; *New project from it* makes a project that takes the Library's loose atlas entities (imported without a project) along with the analytics; over MCP, `project_template {action:"apply"}`. A template is an aegraph document with a `template` block (`id`, `label`, `requires` — the types it draws over — and `home`); the shipped ones are built by `scripts/<template>/build.ts` into `public/templates/`.

### Upgrading an older browser Library

If startup reports an older Library format, its database is preserved and the upgrade is refused. Open it with the previous app version and export your projects before upgrading. Do not clear site data to dismiss the error: that would delete the remaining copy. Keep exported bundles in a backed-up folder; browser storage and browser stashes are not independent backups.

Each project remembers the tabs in Unigraph and in the document, media, map, ontology and analytics sections. Switching projects restores that project's tab arrangement, so returning to a Unigraph session restores its own filters rather than another project's session. The `project_open` tool uses the same switching behavior.
