# `src/core` — the entity system and everything pure

Nothing here renders. Every module is data in, data out, testable in node (`__tests__/` beside each), and the features are projections over it. If you can express a change here, do it here — the pages then get it for free, and so do the tools.

## Invariants worth knowing

- Entities are plain, immutable objects; the store replaces an entity on update, so anything keyed by entity identity (`WeakMap` caches, memoised rows) is safe.
- `store.version` bumps on any write, `store.dataVersion` only on data changes (not bookkeeping such as `accessedAt`): memo over the dataset on `dataVersion`. The active scope's set and its type tallies follow each write (`scopeCache`, `scopeWrite`, `tally`), so `all()`, `countByType`, `countByTypeAndKind` and `types()` under a project never walk it again for an edit. A memo over a whole scope that hands an array to React should keep the previous array when the new one has the same members (see `allGeo` in `features/maps/maps.ts`), so work keyed on its identity stands through a write elsewhere (a commit landing).
- **Memory is measured, not assumed.** A big project (the 689k-tree demo) is the test: `docs/proposals/memory-2026-09-26.md` has the method (`mcp/drive.mjs` on a production build, `HeapProfiler.collectGarbage` then `Runtime.getHeapUsage` at each stage) and what is still open. A cache over every entity is a cache for a burst and is released when idle; a second full copy of the project, even briefly, is the thing to design out — a tab dies at its peak.
- **A load indexes only what the first picture needs.** Loading a big Library (`persistence.ts › loadInto`) hands the pages straight to the store in order — the store's own "a second write of an id replaces the first where it stands" is the merge, so no `Map` of every entity is built on the way — and the store leaves two things behind: the **tag index** (`byTag`, built in idle slices after boot — `providers.tsx › warmIndexesWhenIdle` → `EntityStore.warmTagIndex` — or at once by whoever asks first; `tagCursor` is a handle, and writes keep the index level only for handles it has passed, so a half-built index is always exact) and the scope's **tag counts** (`scopeTagCounts`, counted on first ask). Relationship ends are one id, a short array or, past 64, a `Set` (`Ends`, `addEnd` / `delEnd`), not a `Set` per end. On the WildChat atlas (2.1 M records, dev server, alternated with `main` on a loaded machine) a cold reopen of its Unigraph page drew the positioned scene at 10.6–12.0 s instead of 14.7–16.3 s, the longest freeze 7.5–8.2 s instead of 10.7–11.6 s; `lazyTagIndex.test.ts` and `relationshipEnds.test.ts` pin the answers. The columnar core in `docs/proposals/store-core-2026-09-29.md` is the next step and replaces these.
- **The store's tallies are part of writing an index, not something counted later.** `entityTypeCounts` / `relationshipTypeCounts` (behind `countByTypeAndKind`), the scope's `tagCounts` (behind `tags` and `tagUsage`) and `relStructure` (which keys the cached `relationships()` array) are maintained in `index` / `reindex` / `unindex` / `tally` / `scopeWrite`. Touch one of those and you maintain all of them: every consumer asks for these after every write, and at a million entities a walk to answer was most of a second each — `store-incremental.test.ts` pins them as identities and totals rather than as timings. `searchTextOf` caches on the entity under a non-enumerable symbol (a `WeakMap`'s lookups were 62% of a warm text scan); an edit makes a new object, which has none, so nothing goes stale — and every text built is let go 30 s after the last was asked for (`SEARCH_IDLE_MS`, `releaseSearchText`): it is a cache for a burst of searches, and kept for good it was 386 MB on 700k trees.
- `importBundle(store, doc, { normalized: true })` takes entities in the app's own shape without the lenient per-entity normalisation — the pack (`.aeb`) path uses it; JSON from anywhere goes through `normalizeEntity`. An entity already marked with the bundle's project and new to the Library goes in as the very object decoded.
- Sorting rows for a table: `sortRows` in `features/resources/EntityTable.tsx` ranks the distinct keys once and sorts a packed `rank·n + index` typed array (stable, native), and remembers the result per rows array — the pattern for ordering hundreds of thousands of rows on the main thread.
- Every `data.*` key the app reads is a property some type declares or a well-known key of a registered type — and is in `src/docs/spec.md` and the JSON schema. A new one goes in all three places.
- A type's fields are `BASE_FIELDS` + the code definition + `schema:type` properties, up the parent chain, then the table layout in force (`applyLayout`); the label column is always first.
- **A write is never lost quietly.** `persistence.ts` queues the store's writes; one that fails drops the connection, opens a new one and tries again (`ATTEMPTS`), and what still fails stays queued, written before the next write or on `retry()`, with the status `error` and `unsaved` until it lands — `providers.tsx › PersistAlert` puts that on screen, `app_diagnostics` reports it as `saving`. A page's number is read from the last page on disk inside the transaction that writes it: several writers share the database (tabs; in development, the instance a hot swap left behind), and numbers counted from what each last read overwrote each other's pages. A page write is the newest word on its ids: in its own transaction it deletes their overlay records and tombstones, whichever tab wrote them. **Nothing is deleted before what replaces it is on disk:** compaction (at a tab's own load only) writes fresh pages above the old, then in one transaction deletes exactly what the load read — its pages, the overlay records still as read, its tombstones — never `clear()`, and gives up (deleting only its own pages) if another writer put a page down since the read; a replace (a `reset` batch: an import in replace mode, a cleared Library) writes the new contents first and then deletes, in one transaction, the keys on disk when it began — a crash between leaves old and new side by side, never nothing. An entity no browser can store (a value IndexedDB or the pack cannot take) is not retried forever: a write that fails for good is applied again one record at a time (`applyEach`), and what still cannot be stored is set aside (`status.lost`, `lostIds()`) so the writes after it land — the status stays `error` and `PersistAlert` says to export what was set aside, which the store holds until the page closes. A page that cannot be read is left out of the load, counted (`status.skipped`) and never deleted, and a load that finds a page it listed gone (another tab compacted meanwhile) reads again. Where there are Web Locks, writes and reads hold `aegraph-persistence` shared and compaction exclusive. Another tab's change (BroadcastChannel, listened to from construction; what comes before `attach` waits, in order) is read from the database first and applied afterwards as the difference — changed entities upserted, missing ones removed, unchanged ones keeping their objects — never by clearing the store: the open project stays, an entity this tab changed since the message keeps this tab's version, and nothing is applied while the store has a transaction open (`store.inTransaction`, `store.afterTransaction`). The workspace is the only copy, so the boot asks the browser to keep the origin's storage persistent (`Persistence.keepStorage`, feature-detected, never awaited, never throws); the Projects page's storage card shows the answer. `app/unsaved.ts` makes the browser ask before the page unloads with writes pending or failed, and the app's own reload for a new version waits for them. The store and its persistence are one per page: `AppProviders` keeps them in the module's hot data and boots once per store, so a dev server's hot swap neither makes a second store nor reads the database back over one whose writes are still queued. A load that fails leaves the database unattached: the boot (`providers.tsx`) seeds nothing over a database this browser has (`unsaved.ts › databaseExists`; unknown counts as "has"), keeps a Reload notice on screen, and counts every write to the store as unsaved (`unpersistedStore`) — never attach, seed or migrate after a failed read. Tests: `entity/__tests__/persistence.test.ts` (fake-indexeddb), `app/__tests__/unsaved.test.ts`.
- Writes go through the constraint guard; `store.transaction()` collapses a bulk load into one notification and one judgement.
- The loader is lenient (anything with an `id` gets in); the validator is strict; producers build to the validator.
- **A boot upgrade runs once per database and only on what the old app wrote.** `resources/migrate.ts` steps are listed in `MIGRATIONS` and logged (`storageMigrationLog`, localStorage `aegraph:migrations`); a new database is logged without running. A step matches the old app's shape of the data and a creation date before `resources/legacy.ts › LEGACY_BEFORE`, never a type name alone — `music`, `place`, `display`, `shows` are anyone's words, and a bundle opened later must not be rewritten at the next start. A new upgrade: a new id at the end of `MIGRATIONS`, a matcher on the old markers, a test that a same-named type of someone else's is left alone.

- **Database upgrades preserve old data.** There is no verified IndexedDB v1 migration. `persistence.ts` aborts that upgrade transaction and asks for an export with the previous version; it must never delete old object stores to start fresh, and a later version migrates what it changes and keeps the rest. The preservation regression uses an unknown legacy store deliberately.

- `projects/active.ts` lists every pane host in `PROJECT_UI_KEYS`. Adding a host requires adding its storage key there: a shared Unigraph host otherwise reuses the outgoing project's session and filters. `projects.test.ts` checks parity with `HOSTS`.
