# `src/features/gpugraph` and `src/core/packed` — the engine

The engine that draws the graph explorer's picture — **Unigraph** in the sidebar (`/unigraph`, a pane host whose tabs are `/unigraph/2d` and `/unigraph/3d`, `UnigraphWorkspace.tsx`; the shell is `src/features/graph/`): it consumes the explorer state (`useExplorer()`) and reports back through the same reducer, so every panel, scene and `graph_*` tool works on it. It replaced the sigma 2D and three.js 3D renderers (deleted; `/graph/*` redirects here) and draws everything they drew — the four node shapes, curved parallel edges, edge labels, the placement overlay — for graphs they could not: the target is a million nodes and two and a half million edges, and the rule that makes that possible is the one to keep when changing anything here:

> The cost of a frame follows what is on screen; the cost of an interaction follows the interaction; nothing follows the size of the graph.

## Rules

- **No objects per node or edge on a hot path.** Ids become indices at the boundary (`compile.ts`, the tool); inside, everything is a typed array or a bitset. A `Map<string, …>` in the engine is a bug.
- **Upload what changed, never buffers.** Mutations `mark()` an index into a `DirtyBlocks`; `renderNow` uploads the changed blocks as a few runs only. A new feature that changes per-node data adds a bit or an array and marks — it does not call `allocate` or re-upload everything.
- **Selection is a bitset.** Change membership, then flip flags for the nodes whose membership changed; `afterSelectionChange` recomputes the neighbourhood (`around`) only while the selection is under `AROUND_MAX_SELECTED`.
- **The grid is rebuilt on commit, not per frame.** A drag moves positions and leaves the grid stale; the drop's `commit()` rebuilds it (O(N) — 18 ms at a million). `pick()` excludes `dragging` nodes meanwhile. While the physics runs, `renderNow` leaves a stale grid alone (the in-view count is an estimate anyway); an interaction's `gridNow()` and the stop rebuild it.
- **React sees no frame.** The engine emits events; the view dispatches to the explorer; the HUD samples `stats` a few times a second. Never put per-move state in React. A view behind another page or tab calls `engine.setPaused(true)` (from `useViewActive`): no frames, no physics steps, until it is in front again. It is also hidden, and a hidden element measures nothing: the engine ignores a resize to a collapsed container rather than take the zero for a size, which would shrink the canvases and their buffers and throw the drawn picture away — `mcp/smoke/24-scene-kept.mjs` watches for that across a round trip through the sidebar.
- **The first picture arrives with its camera.** `restoreCamera` in `GpuGraph.tsx` gives a picture its first camera — the fit, and over it a remembered camera or a scene's that still frames it — only once the canvas is measured and the extent is there, retrying from the rebuild, the positions effect and the engine's `resize` event; the host stays `visibility: hidden` until the frame drawn with that camera is in (the engine's `frame` event), so no frame is ever shown framed one way and then jumped to another. `restoredFor` and the reveal are reset when an engine is created: React's development re-run of the effect destroys the first engine before it draws, and the second must not inherit a restore that happened to the first.
- **Both backends stay equivalent.** A shader change is made twice (WGSL and GLSL) and checked on both: the headless driver with `GL=1` gets WebGL2 (SwiftShader), `GL=hw` gets WebGPU on the machine's GPU. `half` is reserved in GLSL ES; int precision must match across stages.
- **Both dimensions stay one engine.** Positions are always x, y, z; the matrix decides. A feature that reads screen positions uses `projectNode`, not `camera.screenX`.
- **Measure before merging** (the root rule for redrawing pages): `gpu_graph benchmark` at 200k and 1m with `GL=hw`, and read the page's `gg:*` marks (`gg:compile`, `gg:positions`, `gg:grid`). Numbers on record (Apple laptop, WebGPU, 1m preset, 2.5M edges): load ~0.6 s, first frame 33 ms, camera frames p95 0.2 ms CPU, select-all 10 ms, filter 46 ms, drag one node < 1 ms/frame, coarse layout 1.9 s in the worker; the GPU draws the fitted picture in 10 ms in 2D and 8 ms in 3D (edges 1–2 ms with the stride, the rest the million dots — nodes are the floor now), a zoomed view in 6–8 ms. The 200k preset draws in 3 ms.
- **A mark on the timeline goes through `lib/measure.ts`.** `measure(name, …)`, not `performance.measure`: the timeline keeps every measure until it is cleared, and the engine's are taken per commit, per pick while physics runs, per hand-back — `measure` keeps the last 500 of each name, which is all the profiler and the headless checks read.

## Adding a capability

State → `GraphEngine` (array/bitset + flag bit + a method that marks) → the shaders if it draws differently → `GpuGraph.tsx` if the explorer state feeds it → the `gpu_graph` tool if it is not reachable through the explorer's own tools → `src/docs/explorer.md › The GPU renderer` → this table.

## Known limits and follow-ups

- The engine's own `layout()`/`relax()` (worker) serve benchmark graphs; the explorer's picture goes through the explorer's layouts so the Layout tab, the badge and the tools agree. Do not add a second position channel.
- The draw still follows the graph, not the view: nodes are `draw(4, nodeCount)` and edges the stride-sampled whole set at every zoom, so a close view at 1m transforms every node and edge. Two routes, both open: a draw-order permutation by grid cell (a Morton order of the cells, rebuilt on commit) so a view issues one draw per few contiguous runs — it must be a permutation the shaders index through, not a renumbering, because node indices are stable across slices by contract; or a compute pass compacting the visible indices into an indirect draw (WebGPU only, so the permutation is what keeps WebGL2 level).
- Far out (regime 0) the million dots are most of the 10 ms frame and most land on a pixel already drawn: a one-node-per-pixel-bucket subset chosen when the camera stops, or an additive splat into a density texture, would make the far view cost pixels rather than nodes.
- The main thread's boundary is now the slow part of a filter or style change, not the GPU: `GraphSlice` is objects and `compile.ts` looks every node and edge up by string id. A packed mirror of the store (type ids, tags as bitsets, a style class per node) would make filtering bitset work and compile a copy — the largest item here, and one that crosses into `core/`.
- Smaller: edge records are 16 bytes (colour and flags could share a word); in 3D the 40k-node in-view sample is projected on the main thread on every camera move; the label pass and the grid rebuild could move to the worker.
- Label propagation merges most of a dense generated graph into one community; the engine's own `coarse` (benchmark graphs, `gpu_graph layout`) still uses it and places one disc, and so does the seed of Force (Unigraph) (`layouts.ts` › `unigraphForce`). The explorer's Multilevel uses Louvain (`louvain.ts`: top-level modularity 0.82 on an 800k generated graph against 0.77 for label propagation, which also puts nearly all of it in one blob); pointing either at `layoutMultilevel` would give them the same picture.
- Multilevel's remaining costs at 800k: the page's `packSlice` (a Map of ids, 1.8 s in Chrome) and `unpackPositions` around the worker, and Louvain's first level (~1.2 s of intrinsic work: it converges in ~4 passes, so the pass cap is not the lever).
- **The force model's defaults are measured, not guessed.** A layout-quality benchmark (2026-09-29; stress, neighbourhood preservation, community purity, edge crossings and node overlap over planted communities, a grid, a tree, a scale-free graph and two real datasets, 212 to 200,000 nodes, against ForceAtlas2) set `linkStrength` 1, `gravity` 0.1, `softening` 0.1 and `alphaDecay` 0.0045 (≈1,500 iterations; `coolingSteps`/`decayFor`); the old 0.35 / 0.25 / 0.5 / 0.02 froze after 342 iterations, left grids crumpled and 10–30% of nodes on top of one another. `packingSpacing` says how far apart those settings pack, which `packingLinkLength` divides by to keep a picture's extent — change gravity or repulsion defaults and it follows. Change a default only with the benchmark rerun on both the CPU model and WebGPU (`GL=hw`); the scripts are a benchmark kept outside the repo.
- **Memory gates a draw, not just size.** The engine's budget (`GPU_VIEW_BUDGET`, 2M nodes / 10M edges) is what it can draw, not what a tab can hold: the WildChat atlas with its filter cleared (1M nodes, 1.09M edges) took the JS heap from 1.47 GB to a 3.26 GB peak (74% of Chrome's 4.4 GB limit) plus 0.3 GB of typed-array buffers, and a real Chrome tab that started higher closed. `memoryGates` (`core/graph/budget.ts`) holds any view past `MEMORY_FLOOR` whose `drawCost` (`DRAW_BYTES`, measured) would take the heap past `HEAP_CEILING` of `performance.memory.jsHeapSizeLimit` (a fixed `UNMEASURED_BUDGET` where the browser does not report it); the explorer reads the heap once per slice, exposes `gateReason`/`heap`/`drawBudget`, and the gate trims to `memoryBudget`. A memory acceptance is `memoryAccepted` — never saved, so a reload asks again. `graph_filter` and `graph_state` apply the same rule (`reason: 'memory'`). Re-measure `DRAW_BYTES` if the engine's per-node memory changes; demo cards past `HEAVY_ITEMS` (`projects/heavy.ts`) warn before opening.
- **Layouts that do not scale have a hard limit** (`LayoutInfo.maxNodes`, `layoutTooBig` in `core/graph/layouts.ts`), measured on sparse community graphs at about twenty seconds a run: the picker greys them out, `graph_layout` and the headless `graph_scene` refuse them, and `runLayout` (explorerState) switches a view past the limit to Force (Unigraph) where the renderer runs it natively, Multilevel otherwise. Force (Unigraph) is the explorer's default (`initialState`); a saved state on `force` moves over once per session key (`:unigraph-default`). Re-measure with the layout-quality benchmark (kept outside the repo, timing) before moving a limit.
- **A big view's held positions are read at boot** (`main.tsx` › `prefetchHeldPositions(sessionsToRestore(…))`, `graph/heldPositions.ts`): the sessions in the address and in front in each pane's saved tabs, read from IndexedDB beside the Library's load and cached (not handed over once — React's development double mount asked twice) until saved to or two minutes pass. The restore then builds the held store straight from the packed columns (`PositionStore.fromPacked`) and lands it with `restored` in one dispatch — no million-key object, no second copy. Marks: `gx:restore-read`, `gx:restore-hold`. At a million nodes the banner went from 3 s (the read started only once the explorer mounted, ~19 s in) to ~1 s, read 51 ms. What is left of a reload there is the Library's load (~10 s) and filter/style/compile, each run twice under React's development StrictMode.
- **The grid moves every iteration** (`SHIFT_CELLS`, `gridShift`, `shiftedGrid`; `P.shift` and `shiftOf` in WGSL): up to four finest cells by a hash of the iteration, the box grown to hold it. A grid that stood still printed itself on dense clusters — every approximation (a cell's nodes as its centroid, each coarser ring as its cells') is anchored to it, so nodes settled in rows and columns (nearest neighbours along an axis 37–39% of the time at 200k–1m nodes, where random directions give 22%), and a finer grid (1024² tried) only moved the pattern to a coarser level. Moved, the errors average out: 23–25%, stacked nodes halved, no loss on the quality benchmark. Positions are read relative to the moved centre everywhere; gravity, springs and the step stay in world coordinates.
- **NaN cannot spread.** The extent pass once took the largest coordinate by its bits, and a NaN's bits beat every number: one bad node made the box NaN and every node NaN the next step. Now a non-finite coordinate never sets the box or enters a cell, a node found at one restarts near the centre (`jitter`, the same hash on both sides), and a force that is not a number moves nothing — on the CPU and in WGSL, where the test is on the exponent bits because a compiler may assume no NaNs and fold `x != x` away.
- The physics (Apple laptop, WebGPU, packed pictures): 1m preset 8 ms an iteration (far field 4, forces 4, the rest under 1), 200k 2.8 ms, 10k 0.5 ms; through the frame loop with the draw, 100 iterations/s at 1m in 3D, 240 in 2D, 235 at 200k. Its rules: the model lives once in `core/packed/physics.ts` and the WGSL mirrors it — `mcp/drive.mjs` steps in the scratchpad compare `GpuPhysics.readBuffer('vel')` after one step with the worker's `physicsStep` from the same positions (they agree to the float); WGSL reserved words (`active`, `self`…) are not identifiers (the shader then fails silently — `getCompilationInfo` now reports it as a physics error); a stage may bind eight storage buffers, so the extent shares the cell buffer. The nodes are sorted by finest cell every iteration (a counting sort: bin, a three-dispatch prefix sum, scatter), for the own-cell repulsion: with it the 1m atlas steps in 14–15 ms where it took 12, a 100k graph in 0.6–1.2 ms; the bin writes each node's cell into the velocity's fourth word and the scatter reads it, since two kernels can round the same arithmetic differently and a node on a cell's edge was counted in one cell and written into the next. Dense clusters settle as clouds only with both halves of the fix: the own-cell pairs (without them nodes in one cell never push each other, and pile into rings around a hub or spokes out of it) and `springJitter` (without it a hub's identical springs still pack the leaves in shells) — `core/packed/__tests__/physics.test.ts` holds both. Not tried yet: running the forces kernel in the sorted order so its reads are coherent; a Morton layout of the cells; propagating the far field down the pyramid (L2L) instead of walking the rings per cell — each a candidate for 2× on the kernels. A cutoff on the repulsion was tried and rejected: which cells count then depends on the cell a node is in, and the nodes lock onto the grid's lines. With the edge stride the draw at 1m fell from 30 ms to 10, so the physics gets 3–5 iterations a frame: 240 iterations/s at 1m in 2D, 100 in 3D. Every edge is still transformed when zoomed in (no culling by view): a compute pass that appends the edges in view to an indirect draw would be the next lever there.
- Node shapes are two flag bits and a distance field in the node shaders; a parallel edge's curvature is a signed byte in bits 8–15 of the edge flag word and the edge quad is a strip of `EDGE_QUAD_VERTICES` along the quadratic (lines far out stay straight); edge labels come from walking the incident edges of the nodes in view. Node images and node borders are not drawn.
- In 3D the label candidates and the in-view count come from a sample of up to 40k projected nodes.
