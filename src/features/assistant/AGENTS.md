# `src/features/assistant` — the tool set and the panel

One set of tools serves three callers: the in-app assistant panel (`AssistantPanel.tsx` — and the Chats page, `features/chats/` — both rendering a chat through `ChatThread.tsx`, streaming through `src/core/ai/client.ts`), Claude Code through the bridge (`mcp/server.mjs` lists exactly the manifest the tab sends), and the app's own voice control. **A feature reachable from the UI must be reachable here** — that is the parity rule in the root `AGENTS.md`.

## Writing a tool

1. `betaTool({ name, description, inputSchema, run })` in the file for its area (a new area gets a new `*Tools.ts`). The `description` and each parameter's `description` **are the documentation** — `/docs/assistant` generates its reference from them. Say what the tool does, what it returns, and what to call first when there is a natural order (`list_properties` before `set_properties`).
2. `inputSchema` is a JSON Schema with `additionalProperties: false`; one tool with an `action` enum (`constraint`, `script`, `project_*`) beats five tools when the actions share a subject.
3. `run` returns `json(...)` (a string of JSON) or content blocks (an image). Throw an `Error` with a sentence for anything the caller can fix; the wrapper turns it into the tool error the model reads.
4. A tool that shows something also writes it to the ES (`globe_load`, `add_path`, `diagram_to_dataset`), and a tool that changes data goes through the store so constraints, versions and the UI all see it.
5. **A tool that creates an asset opens it.** A new document, image, video, audio, diagram, map, entity, dataset, chart or script is put in front of the user by default through `openMade(host, id, path)` (`toolkit.ts`), with an `open` parameter (default true) to make it quietly. `openMade` asks `host.reveal(id)` first — on the Chats page (`useAppHost`) that opens it as a tab in the chat's artifacts panel, the chat staying put — and navigates to `path` otherwise. Never `host.navigate` a new asset directly: on the Chats page that would take the user away from the chat. Updates don't open; the caller asks for that (`open` actions, `inspect`).
6. Register it: add to the list in `tools.ts` (`createAppTools`), and to the sorted name array in `__tests__/assistant.test.ts` (the test fails until you do).
7. Test it in `__tests__/<area>Tools.test.ts` with a store and a fake host (`setup()` in `moreTools.test.ts` is the template; wrap the tool in `withInputChecks` so the schema is checked as it is at run time) — the tool's parse-and-run path, including one error. `toolCoverage.test.ts` fails for any tool no unit test runs; a tool covered only by a smoke step goes on its `SMOKE_ONLY` list, which is checked both ways so it only shrinks. A view the tool drives is faked through its handle (`globeTools.test.ts`, `captureVideoFrame.test.ts`); a heavy module it reaches is mocked (`viewDiagram.test.ts`, `chatTools.test.ts`).
8. If it needs a mounted view (a graph, the globe, a player), reach it through the page-global handle (`explorerHandle`, `__aegraphGlobes`, the media handles) and answer clearly when nothing is mounted.
9. **Untrusted input.** A tool's arguments may have been written by a bundle or a page the model read, not the user. A tool that fetches a URL it was handed uses `fetchHandedUrl` / `approveHandedUrl` (`toolkit.ts`, over `core/net/url.ts`) — never a bare `fetch(url)`; `view_image` fetches a remote picture in the tab after that question and returns pixels, never a URL; a tool that writes an address a view will load (`data.src`, `url`, `image`, `thumbnailUrl`, `screenshotUrl` — `LOADED_URL_FIELDS`) calls `approveLoadedUrls` first (`web_fetch` is the one exception, with the same classification and a per-host yes, because reading a site is many requests) — so this origin goes through, anywhere else needs Third-party services and `host.confirm` naming the host, and headless never reaches a private address. A tool that loses work, or changes a setting that governs the network calls `host.confirm` itself, whatever the caller, with no argument that skips it — and says what yes does: `host.confirm(message, { yes: 'Delete', danger: true })` for a loss, `{ yes: 'Allow' }` to reach a host (no options: a plain **Yes**; the card, the bridge's dialog and voice all use the word) (the old `unsaved:"discard"` did; it asks now). Pass `kind: 'fetch'` when the question is about reaching a host. **Every label in a question goes through `quoteLabel` / `oneLineLabel`** (`core/entity/entity.ts`: one line, clipped, control, direction and zero-width characters out), counts first — a label is someone else's text, and unquoted it can dress itself as the question; `<app_context>` quotes labels, titles, paths and ids the same way. A delete of something with text of its own (a slide, a block, a point, a chapter; a story or a deck with what hangs from it) asks `{ yes: 'Delete', danger: true }`; the microphone (`voice {listen}`) asks every time. A tool that runs a saved script passes its `scriptId` (`script {run, id}` does), so code its owner has not run here runs untrusted (`features/scripts/consent.ts`). Tests: `handedUrl.test.ts`, `untrustedWrites.test.ts`, the confirmation cases in `accountTools.test.ts`, `versionTools.test.ts`, `memory.test.ts`.
10. Mention it on the feature's docs page where the feature is described ("Over MCP: …"), and in `src/features/AGENTS.md` next to its page.

## The app context

Every message carries `<app_context>` (`useAppHost.ts`): route, the open document or entity, selected text, the playhead of an open video or track, the open project with its HEAD and unsaved counts, which docs page is on screen, whether voice is on. When a feature has state the assistant should not have to ask for, add it here — briefly. Text that came from the data rather than the user — selected text, the detail pane, shared notes — goes in through `untrusted()` in `session.ts` (an `<untrusted_data source=…>` wrapper that the text cannot close), and the system prompt's *Whose words are whose* says what that means; add new free text the same way.
