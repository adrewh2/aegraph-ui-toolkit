# `src/headless/` — aegraph with no screen

The app is a renderer over a logical engine: an entity store, an ontology, filters, layouts, metrics, projects, versions, constraints, scripts. None of that needs a DOM. This folder hosts that engine in Node and serves the app's own tools over MCP, so a project can be created and managed — and a scene composed — with no browser open.

| File | What it is |
| --- | --- |
| `engine.ts` | `HeadlessEngine`: one workspace file (`.ae.json`, gzip optional) read at boot and written back 250 ms after every data write, the open project remembered in it, and `host()` — the `AppHost` the tools take, with `confirm()` answering by how the engine was started: a question of kind `fetch` (a tool about to reach a URL it was handed — an image, a bundle, a page) by `--allow-network` (`allowNetwork`, off by default), any other by `--yes` / `--refuse-destructive`. |
| `tools.ts` | What the engine exposes: the app's tool groups minus the ones that need a browser (the `NEEDS_A_SCREEN` list), plus the ones below. |
| `workspaceTools.ts` | `workspace_status` / `save` / `reload`, `open_project`, and `import_file` / `export_file` — the Projects dialog as a path. |
| `graphTools.ts` | The graph computed rather than drawn: `graph_slice`, `graph_metrics`, `graph_layout` (which reports a tree's roots, depth and undrawn cross-links). |
| `sceneTools.ts` | `graph_scene`: composes data + filter + layout + style + the view metadata (camera, toggles, selection, the 3D slide layer’s decks and focus) into the same part entities the explorer's `graph_save` writes, so the app opens exactly the picture composed here. With no canvas, the scene's card picture (`data.preview`) is drawn from the slice and its positions by `core/graph/thumbnail.ts`. |
| `historyBlobs.ts` | Commit content on disk (`<workspace>.history/<commit>.json.gz`) where the browser uses IndexedDB, so `project_commit` in one process and `project_restore` in the next behave as they do across reloads. |
| `server.ts` | The MCP server: stdio, or `--port` for streamable HTTP so several clients drive one running instance. A lock beside the workspace keeps it to one writer. |
| `results.ts` | What a tool hands the client: every text block, and a tool's error, framed in `<untrusted_data tool="…">` by the bridge's own `mcp/frame.mjs`, under `HEADLESS_INSTRUCTIONS` — the workspace's text reaches a developer's Claude Code as data, never as an instruction. A client that reads results as JSON calls `unframe` (`mcp/smoke-headless.mjs`, the Aurora demo's generator in aegraph-ui-demos). |
| `paths.ts` | `PathRoot`: the one directory `import_file` / `export_file` may touch — the workspace's, or `--root`. Symlinks resolved before judging a read; never written through; never into `.git`, never through a dotfile or dot-directory (the root is often a home: `.ssh`, `.env`). |
| `httpGate.ts` | Who may speak over `--port`: a loopback `Host` only (DNS rebinding), no browser `Origin` unless `--allow-origin` names it, and a bearer token (`AEGRAPH_HEADLESS_TOKEN`, or one printed at startup). |
| `publicFetch.ts` | The process's `fetch`, installed by `server.ts` before any tool runs: GET/HEAD over http(s) to public addresses only, checked in the connection's own DNS lookup (`mcp/publicUrl.mjs`), redirects checked hop by hop (and answered rather than followed under `redirect: 'manual'` or a `follow` that says no — `web_fetch` asks about a new host first, the dev server's `/api/fetch`, `dev/fetch.ts`, follows the same host only), body capped. A handed URL can't reach the loopback, the LAN or a metadata endpoint. A tool that needs something else from the network needs a reason and a change here. |

Built with `vite.headless.config.ts` (one SSR pass, dependencies external) because app modules reach for bundler-resolved imports — `?raw`, a `.py` prelude, a stylesheet beside a component. `npm run headless -- <file>`; `npm run smoke:headless` is the end-to-end check with no browser anywhere.

## Rules

- **The tools are the app's tools.** A capability belongs in `src/features/assistant/*Tools.ts`, where both hosts get it; this folder adds only what has no meaning in a tab (the workspace file) or no renderer to ask (the graph, computed). If a headless tool starts to duplicate a browser one, the shared part belongs in `src/core/` — as the style channels do (`core/graph/styleChannels.ts`, used by `graph_style` in the tab and `graph_scene` here).
- **What a tab has, this has not.** No camera to read, no canvas to snapshot, no player, no workstation, no `localStorage`. A tool that would answer "it is now on screen" is excluded in `tools.ts` rather than made to lie; one that needs a *number* a renderer owns (a 2D camera's zoom, which is a ratio of the renderer's own fit) leaves it out and lets the app supply it.
- **One writer per workspace.** The engine autosaves; two processes on one file would overwrite each other. The lock is advisory and `--force` ignores it, but the answer is normally a port.
- **A path from a tool call goes through `engine.paths()`.** A model writes the path, and a model can be talked into `~/.ssh/id_rsa` or `~/.zshrc` by what it read. Every tool that touches the disk with an argument resolves it with `forRead` / `forWrite` first, and writes with `O_NOFOLLOW`; the engine's own files (the workspace, its lock, `.history/`) are named at startup and are not arguments. A new tool that reads or writes a path does the same, with a case in `__tests__/boundary.test.ts`.
- **Handed URLs: declined unless `--allow-network`.** The developer's Claude Code asked to run a tool, not to reach whatever host its arguments — written by the data or the model — name; `HEADLESS_INSTRUCTIONS` says so. A new tool that reaches a handed URL asks `host.confirm(…, { kind: 'fetch' })` through `approveHandedUrl`, and gets this answer.
- **Destructive tools: allowed over stdio, declined over a port.** Over stdio the client is the developer's own Claude Code, whose permission prompt stood in front of the call. Over `--port` any holder of the token is a client, so the engine declines them unless started with `--yes` (or `AEGRAPH_HEADLESS_CONFIRM=allow`); `--refuse-destructive` declines them on stdio too.
- **Arguments are checked for shape before any tool runs** (`features/assistant/validate.ts`, shared with the tab): the schema, and under it caps on array length, string length, depth and prototype keys. A tool that takes a dataset in one call is in `BULK_TOOLS`.
- **Anything authored here is checked in the app.** `mcp/smoke/27-aurora-analytics.mjs` opens what the engine composed (Aurora's scenes, scripts and charts — the Aurora demo's generator in aegraph-ui-demos drives this engine to write them) in a real tab and asserts the picture: the counts, the parts it loaded, and that it opens framed.

- **File tools obey destructive policy too.** Reload with unsaved data, replacement imports, imports colliding with existing IDs, and export overwrites require destructive access. Refusing overwrites uses `O_EXCL`, so a file appearing after path validation is protected too. Autosave failures retain the live workspace and expose `saveError` through `workspace_status`; `workspace_save` retries.
