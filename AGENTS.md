# Working on aegraph-ui-toolkit — notes for agents

Read this before changing code. It holds the vocabulary and the working rules that are not derivable from the code itself. `README.md` describes the architecture; `docs/proposals/` holds reviews and plans; `docs/configuration.md` is every environment variable (where it is read, build time or runtime, secret or public, what breaks without it) and what a fork for an organisation changes — a new variable goes there, and in `.env.example`, in the same commit; `src/docs/*.md` is the in-app documentation (the product manual). Each area of the tree has its own `AGENTS.md` with the map of that area — read the one for the area you are changing:

Every project the app offers to open — Aurora, China tour, Knowledge Infrastructure, AcademicsKG, the DBpedia sample and the rest — reaches a build, with no checkout and no token, from the copies aegraph.dev publishes (`AEGRAPH_DEMOS_SITE`, `scripts/demos/fetch.mjs`). They are built in the private repo `aegraph-ui-demos`, whose checkout (`../aegraph-ui-demos` or `~/workspace/aegraph-ui-demos`), or a token for it, takes precedence. This repo carries no project data, and `load_dataset` and the Demos tab reach them by id through the demos catalog.

## Vocabulary

- **ES** — the **entity system**: the store (`src/core/entity/store.ts`), the entity/relationship/type primitives (`types.ts`, `schema.ts`, `typeRegistry.ts`) and everything that reads and writes them. "Load it into the ES" means: create real entities (with types, tags, `meta.source`, relationships) in the store, not a transient view. Every view — tables, graphs, maps, the globe, charts — is a projection over the ES; a feature that draws something the ES does not hold is incomplete.
- **Ontology** — the types, their properties and parents, the relationship vocabulary, and the constraints, themselves stored as `schema:type` and `constraint` entities. See `/docs/about` and `/docs/roadmap` in the app.
- **Inner tabs** — the tabs inside a page, under its title bar: a section's **List** (its index, first, never closed) and what was opened from it, each closable; the Workstation's and Entities' / Unigraph's tabs too. Not the sidebar's entries, which are pages. The owner's word for them.
- **Scope / project** — a project is a named scope over the one Library; `store.scope` is the open project, `store.library.*` reads past it. A project has **versions**: commits, unsaved changes, a history (`src/core/projects/versioning.ts`).
- **Bundle** — a project as a file (`.ae.json`, or the `.aeb` pack) with its `state` (route, UI keys); `project_open_bundle` and the Datasets page open one as its project, on its home route.
- **Layout (table)** — a type definition's `data.table` (columns, hidden, sort) or a map's `data.table` (types, sort): how rows read by default, set by the `table_layout` tool or a bundle.
- **Pick** — a set of ids handed between views through sessionStorage (`storePick` / `readPick` in `src/app/openIn.ts`, `?pick=<key>` in URLs).
- **Explorer handle / globe handle / GPU graph handle** — page-global registries (`__aegraphExplorers`, `__aegraphGlobes`, `__aegraphGpuGraphs`) through which tools drive views that are mounted.
- **Unigraph / the engine** — the graph page (`/unigraph/2d`, `/unigraph/3d`; the explorer's shell is `src/features/graph/`, its one view `src/features/gpugraph/`): the explorer state drawn by `GraphEngine` over packed arrays (`src/core/packed/`). The sigma 2D and three.js 3D renderers and the Graph Explorer page (`/graph/*`, now a redirect) are gone; their scenes load. "Packed" means integer-indexed typed arrays — no per-node objects on any hot path. The **held positions** — the session's working layout — are a granular store (`src/features/graph/positionStore.ts`), never a plain object: a move writes one entry and bumps a version, memos key off `positions.version` and `positions.size`, and `asObject()` is for boundaries only (saving a layout, the handle the tools read, persistence), never a render or a loop. A move of some nodes (a drag, `graph_positions`, a transform, a placement) goes through the provider's `dispatchHeld`, which first holds what is on screen for the nodes the store lacks: over a layout nobody held, a move of one node used to leave the rest unplaced and re-laid-out — the whole graph jumped.
- **Scripts** — code over a read-only snapshot (`src/scripting/`): the JavaScript prelude (`prelude.js`, QuickJS) and the Python prelude (`python/prelude.py`, Pyodide) define one **collections** vocabulary (`entities.types.person.filter({…}).neighbors('wrote')…`) that must stay identical in both — change one, change the other, and the API texts in `src/features/scripts/api.ts` (pairing tests enforce that every global is documented). The editor's completion infers types through the code (`src/features/scripts/infer.ts`) from the data schema (`src/features/expr/schema.ts`) and the vocabulary (`vocabulary.ts`); scaffolds (`scaffold.ts`) write scripts from the real data. Switching a script's language converts it through the assistant only (`convertWithAssistant.ts`, gated on `currentBackend()`; the pair cache in `languageSwitch.ts` restores the other side untouched) — there is deliberately no mechanical converter. A script put to use has a **kind**, a subtype of `script` through `parent` (`script:filter`, `script:constraint`, `script:scene`; `SCRIPT_FAMILY`, `scriptKindOf`, `scriptsIn` in `script.ts` — never `store.ofType('script')` alone): a plain `script` until saved with a kind or first connected (`markScriptUse`) — a filter script's ids become the explorer's `only` + `script` (`filters.ts`), a constraint script is a constraint's `rule.script` (`constraints.ts`), a scene script's scene is a `scene:script`.
- **Dataset kinds** — a dataset read from a file or CSV text has a **kind**, a subtype of `dataset` through `parent` (`dataset:csv`, `dataset:tsv`, `dataset:text`, `dataset:excel`, `dataset:parquet`; `DATASET_SUBTYPES`, `datasetTypeOf`, `datasetsIn`, `isDatasetType` in `core/datasets/dataset.ts` — never `store.ofType('dataset')` alone), set when the entity is made and kept through edits; one a script returned, one made from entities or one typed in is a plain `dataset`. The Datasets list, the sidebar count, the Workstation picker, routes and the `dataset` tool take the whole family.
- **Voice** — `src/features/voice/`: the controller (`voice.ts`), the listeners (browser recognition or OpenAI transcription, `listeners.ts`), the speakers (browser voice or OpenAI neural voice, `speakers.ts`), how OpenAI is reached (`access.ts`: a key of the user's, straight to OpenAI; locally the dev server's `/api/openai` with the key in `.env.local`; otherwise none — the browser's own) and the glue to the chat (`assistantVoice.ts`). The shared chat lives outside the panel (`src/features/assistant/instance.ts`) so voice drives it with the panel closed. Documented in `src/docs/assistant.md` › Voice.
- **Chats** — `src/features/assistant/chats.ts`: the open chats (the panel's tabs), each an `AssistantSession` with its own storage key, one active; `instance.ts` loads them lazily and hands them the app host; voice and "Ask about this" follow the active one; the `chat` tool moves between them. A chat belongs to the project open when it started (`Chats.projectOf`, kept in the list's storage); the registry follows `store.scope` (`setScope`, from the host's store), so the tabs, `active()`, the Chats page (`useChatRows`, over `store.ofType`) and the sidebar count are the open project's, every chat in the Library, and it remembers each project's chat in front. Every chat is recorded as a `conversation` entity (`record.ts`, id `assistant-chat:<chat id>`, source `assistant`) in the project open when it started, written when a message is sent and when the reply is complete (and for changes while idle), never token by token — a record write is a store change, with persistence, versioning and autosave behind it; the transcript survives a reload by its own save (`session.persist`). The list of chats (`useChats`) notifies on a chat's title or busy state only, and the Chats page's list is memoised, paged and keyed off that (`useChatRows`): a Library can hold thousands of imported conversations, and re-listing them per token stalled the tab until Chrome killed it — the ES holds the chat, the panel only shows it. A chat is shown by `ChatThread.tsx` (transcript, pending question, composer), which both the panel and the **Chats page** (`/chats`, `src/features/chats/`) render. A chat's **artifacts** are what it made or changed — the ids named by its *writing* tool calls (`chats/artifacts.ts › isWriterTool`: `create_*`, `write_*`, `edit_*`, `update_*`, `add_*`, `annotate_*`, `graph_save`, …; reads make none) — kept whole in the record as `ConversationData.artifacts` because the record truncates tool results. A new writing tool whose result names its entity as `id` (or its input as `id` / `*_id`) is an artifact with no further work; one that names it otherwise needs a case in `idsOfCall`. A place, path or area on a map (`onMap` in the result, or `map_id` in the input) counts as the map; a file the user attached to a message (`assistant/attachments.ts`: images, documents and data files picked, dropped or pasted into the composer — CSV, TSV, Excel and Parquet as `dataset` entities, a `.txt` as whichever the composer's question says — made entities when the message is sent and named to the model by id) counts under the tool name `attach`. The Chats page opens its panel on its own for one thing: an asset a tool just created (`openMade` in `toolkit.ts` → `host.reveal` → `showArtifact`), which arrives as a tab in front while the chat stays put — off the Chats page the same call navigates to the asset's page. Otherwise only the Artifacts menu, a tool card's Show, or `chat {show}` open it.
- **Assistant memory** — `src/features/assistant/memory.ts`: the assistant's notes for the open scope, a document tagged `assistant:memory` (source `assistant`), read into every turn's `<assistant_memory>` and kept through the `memory` tool. It is an entity like any note: never a separate store.
- **Anything that leaves the machine goes through the switch.** A new call to a third party — a tile server, a lookup, a model, an embed — asks `requireExternalServices('<the feature>')` (or `externalServicesAllowed()` / `useExternalServices()` in a view) from `src/features/account/settings.ts` at its narrowest point, before the request is made, and the view says why it is empty rather than failing silently. Add the host to the tables in [`SECURITY.md`](SECURITY.md) and `src/docs/privacy.md` in the same commit, and a case to `src/features/account/__tests__/offline.test.ts`, which asserts `fetch` is never reached. The dev server's own routes (`/api/*`, on this machine) are not third parties and are not gated. Voice obeys it too: with the switch off the browser's recogniser and voices are used only where they run on the device (Chrome sends audio to Google, Safari to Apple, and its Google voices the text), and adding a YouTube or Spotify link skips oEmbed.
- **Nothing in a sandbox frame is inline script.** A frame inherits the page's Content-Security-Policy — `srcdoc` or loaded from a URL, measured both ways — and its own `<meta>` CSP can only narrow what it inherited. An enforced `script-src` (which the app has) therefore kills an inline bootstrap silently. Both script engines load theirs by URL from `public/sandbox/` and pass everything after it as `blob:` scripts; `src/scripting/sandboxBoot.ts` carries `SANDBOX_PROTOCOL`, to bump in the same commit as any change to the messages an engine and its bootstrap exchange. See `src/scripting/README.md` and [`SECURITY.md`](SECURITY.md) › *Response headers*.
- **What arrives from outside is bounded.** A gzipped bundle goes through `core/exchange/gunzip.ts` (never `DecompressionStream` directly: what a gzip becomes is unbounded and one file could take the tab, and any product embedding this one, out of memory); a field key is checked for `__proto__`/`prototype`/`constructor` before it is walked. An entity's nesting and a pack's size are bounded by `core/exchange/limits.ts` (`MAX_DATA_DEPTH`, `MAX_PACK_ENTITIES`, `MAX_PACK_VALUES`). A table from a file goes through `core/datasets/files.ts` (`readDatasetFile`, `DATASET_FILE_LIMITS`: size, rows, columns, cells, cell text, inflated bytes — refused at the bound with a sentence, never truncated). A graph file goes through `core/exchange/graph/limits.ts` (`GRAPH_FILE_LIMITS`, `checkGraphBytes` before it is read, `checkGraphShape` after, `readGraphResponse` for a download), and an XML one through `parseXmlDocument` (a doctype or entity declaration refused) before any library reads it. New reader, new importer, new decompression: use those, and add the case beside `__tests__/gunzip.test.ts` (or `core/datasets/__tests__/files.test.ts`, `core/exchange/graph/__tests__`).
- **A file changes only what is its own.** A bundle merges into the Library under rules decided once in `core/projects/bundle.ts` (`planImport`, reported without writing by `previewBundle`): new entities marked with the file's project only, that project's own entities updated when newer, everything else left as it is and counted (`BundleConflicts`), no `includes` taken, constraints switched off (`core/constraints/quarantine.ts`). A graph import updates only what an import made unless `reuseExistingIds` is asked for. A new way in that writes entities follows the same rule — and a tool that opens one asks first from that plan (`features/assistant/bundleGuard.ts`).
- **Data is drawn, never run.** Anything from a bundle, an import or the model is data: a rendered diagram goes through `core/diagrams/sanitizeSvg.ts` before it is drawn, and it is drawn as an image (`features/diagrams/DiagramPicture.tsx`, `svgDataUrl`), never mounted as markup (a picture that cannot be cleaned is refused, not shown); scripts run in a sandboxed frame with an opaque origin — `allow-scripts` without `allow-same-origin`, never both; a URL from data is checked for scheme and origin before it is fetched or framed, and one naming the dev server's own routes (`/api/…`) is refused (`isOwnFunction` in `lib/markdown.ts`). **Nothing runs on arrival without consent:** a new place that runs a script by itself asks `autorunRefusal` (`features/scripts/consent.ts`) first, and a run of a saved script passes its `scriptId` so code its owner has not run here runs untrusted. **A figure reaches Plotly cleaned:** mount Plotly through `features/plots/PlotlyChart.tsx`, which applies `sanitizeFigure` (`scripting/figure.ts`), never `Plotly.newPlot` on a script's output. A media player is the provider's page in a sandboxed frame driven by messages (`EMBED_SANDBOX` in `features/videos/youtube.ts`) — no provider script in the app's origin. Adding a place where data reaches the DOM, a frame or `fetch` means the check and a test beside the ones in [`SECURITY.md`](SECURITY.md) › *Data that is drawn and run*. **Nothing from data is compiled in the app's realm** — no `new Function`, `eval` or `setTimeout(string)` over text a bundle, a tool call or a model could have written: a constraint's `rule.js` runs in QuickJS (`core/constraints/realm.ts`), scripts in the sandbox frame. `'unsafe-eval'` is in the CSP for Pyodide only, and the claim that it costs nothing rests on this rule. A colour from data goes through `lib/cssColor.ts` (`cssColor` / `isCssColor`: type colours, style channels, imported node colours), a link or a window opened from data through `httpUrl`, a picture from data — in Markdown, an entity's image property, a thumbnail, a viewer, a map card — through `components/imageGate.ts` (`useImageGate`, drawn by `components/RemoteImage.tsx` › `DataImage`; a CSS background through `cssImageUrl`): shown when it is carried in the data or on this origin, a click on another host (a provider's thumbnail at once, with the switch on), nothing at all with Third-party services off; and "remote" is where the URL resolves (`lib/markdown.ts` › `isRemoteUrl`), not how it looks. A CSV the app writes goes through `lib/csvCell.ts` (`defuseCell`; `restoreCell` when it is read back).
- **Your data and keys never land in the repo.** Four guards, independent on purpose. The app refuses a source checkout as its projects folder (`checkoutKind` in `src/features/projects/folder.ts`, checked at the pick and before every save); `.gitignore` refuses every shape the app writes (`*.ae.json`, `*.aeb`, `*.aegraph.json`, gzipped forms, published `.html`, exports, `public/datasets/*`, every `.env` but the example) and every key or certificate (`*.pem`, `*.key`, `*.p12`, `*.pfx`, `id_rsa*`, `*service-account*.json`) wherever it sits, then allows back the few documents this repo ships (the spec's example, the atlas template) **by exact path**; `.githooks/pre-commit` refuses the same at commit time (a file forced past `.gitignore` with `git add -f` still reaches it) plus anything over 5 MB; `.githooks/pre-push` reads every commit about to be sent, so one made with `--no-verify` is stopped while the data is still local — a pushed pull request is public, and deleting the file afterwards does not unpublish it. What counts as data, and what this repo ships, are written once in `.githooks/data-guard.sh` and read by both hooks and both CI checks; `scripts/__tests__/data-guard.test.ts` runs the real rules and fails when `.gitignore` or CI drifts. A demo project never goes here — it is a generator in aegraph-ui-demos; adding a document the repo ships is a deliberate edit to `DATA_ALLOW`, `.gitignore` and `.github/workflows/ci.yml`, in the same commit. Never widen a rule to a whole directory, never commit or push with `--no-verify` on someone else's behalf, and when you create projects while working here, save them outside the clone. `npm install` installs the hooks through `scripts/hooks.mjs`. See [`SECURITY.md`](SECURITY.md) and the `/docs/privacy` page, which are updated together with any change to what the app writes or what it calls over the network.
- **The dev server's routes** — there are no deployed functions: a deployed copy is a static site with no accounts. The dev server serves two routes of its own, from `dev/` (which Vercel never deploys): `/api/openai` (`dev/openai.ts`: OpenAI's two audio endpoints with `OPENAI_API_KEY` from `.env.local`, 503 without it) and `/api/fetch` (`dev/fetch.ts`: the `web_fetch` tool's reader for pages a browser may not read — GET, public addresses only through `src/headless/publicFetch.ts`, 3 MB of text, same-host redirects only — the one route that reaches arbitrary hosts, so anything that widens it goes through `SECURITY.md` › *The assistant and untrusted content*). Ungated, they answer only the dev server's own page's `fetch` — the exact path, `Sec-Fetch-Dest: empty`, `/api/fetch`'s address in an `x-fetch-url` header (`scripts/devOrigin.mjs` › `localApiRoute`, which maps them to the `dev/` modules, used by `vite.config.ts` › `localApi`) — so an image or a frame written into data cannot reach them; voice on this machine needs nothing else. On a deployed copy `web_fetch` reads only what the browser may. Tests in `dev/__tests__/` and `scripts/__tests__/devOrigin.test.ts`. `.env.example` lists the variables.
- **The assistant reads other people's words.** Entity text, documents, bundles, fetched pages and tool results can carry instructions; the defence is the tools, not the model. A tool that fetches a URL it was handed goes through `approveHandedUrl` / `fetchHandedUrl` (`features/assistant/toolkit.ts`, over `core/net/url.ts`), and one that writes an address a view will load through `approveLoadedUrls`; a tool that loses work, widens access, opens a bundle over the user's entities (`bundleGuard.ts`), changes the assistant's memory or the third-party switch asks `host.confirm` with no argument that skips it, with `kind: 'fetch'` when the question is about reaching a host, and names what it asks about through `quoteLabel` / `oneLineLabel` (`core/entity/entity.ts`), never a raw label; free text placed in the model's context is wrapped as untrusted data. The bridge's chat child (`mcp/chat.mjs`) has no built-in tools and must stay that way; the bridge fetches nothing, routes calls only to tabs of its first tab's origin (or with the token), and cleans what a tab says about itself; tool results reach Claude Code framed by `mcp/frame.mjs`, in an envelope with an id of its own. In headless Node, `fetch` is `src/headless/publicFetch.ts` (public addresses only), a handed URL is reached only with `--allow-network`, and paths go through `PathRoot`. See [`SECURITY.md`](SECURITY.md) › *The assistant and untrusted content*, *The bridge*, *The headless server*.
- **Feature flags** — `src/app/features.ts`: the features a deployment can leave out of its build (`maps`, `globe` — which lives in Maps and goes with it — `videos`, `audio`), set by `AEGRAPH_FEATURES_OFF` at build time (`vite.config.ts` bakes it in as `__AEGRAPH_FEATURES_OFF__`; in Node — the headless engine, the tests — it is read from the environment when the module loads). `featureOn(name)`, `pathOff(path)` and `turnedOff(name)` are what every surface asks: the sidebar (`nav.tsx`, `counts.ts`), the routes (`AppRoutes.tsx` › `gated`, showing `components/FeatureOff`), `entityHref`, the Library's capabilities, the inspector's views, the workstation's views, presets and hosts, the docs pages (`DocPage.feature`), the showcases and the system prompt — and the tools, decided once in `features/assistant/toolFeatures.ts`. A feature's data is never touched: its entities stay in the Library and the tables. **A new feature that can be knocked out registers in `features.ts`**, its tools in `TOOL_FEATURES`, and each surface it has asks `featureOn`; `src/app/__tests__/features.test.ts` and `assistant/__tests__/toolFeatures.test.ts` show how to test a build with it off.
- **Applet** — a viewer/editor for one medium (documents, images, videos, audio, diagrams, maps, conversations) in which the medium stays whole and annotations attach to exact places in it.

## Rules

- Never `git add -A`; stage explicit paths. Check `git status` before touching a file, and leave changes that are not yours alone. Work on a branch of your own (a **git worktree** is convenient for anything beyond a small change: `git worktree add ../aegraph-ui-toolkit-<topic> -b <topic>`, symlink `node_modules`, a local Vite config on another port), run the type-check, lint and tests below, and open a pull request against `main` that says what changed, how it was checked, and what is left.
- Tag related commits with a bracketed group prefix (`[perf]`, `[globe]`, `[tables]`, `[projects]`, …) so a piece of work can be listed with `git log --grep='^\[tag\]'`.
- Type-check with `npx tsc --noEmit -p tsconfig.app.json`; lint with `npm run lint`; tests with `npx vitest run`. The repo has no prettier config — never run bare `npx prettier --write`.
- **Every dropdown is ours.** A choice from a list is `components/ui/Select` — a button showing the choice, its choices in the app's `Menu` (ticked, keyboard-driven, themed) — never the browser's `<select>`, whose look and list are the operating system's. It takes a native select's props and `<option>` / `<optgroup>` children, so write it as you would a `<select>`; `e.target.value` reads the same. `components/ui/__tests__/nativeSelect.test.ts` fails on a native one. Smoke steps drive it with `selectOptions` / `selectPick` from `mcp/smoke/lib.mjs`.
- **Colours are the theme's.** Every colour the app draws for itself comes from a token in `src/index.css` (`--bg`, `--surface`, `--text`, `--select`, `--highlight`, `--overlay`, `--canvas*`, …), never a literal: a tint is `color-mix(in srgb, var(--text) 8%, transparent)`, a shadow `color-mix` with `--shadow-color`, white over a picture `--on-media`. Where Paper's warm tint and a dark theme's shadow cannot be one token, `light-dark(<Paper's mix>, <the dark mix>)` picks by the `color-scheme` the theme sets (`applyTheme`, `theme-boot.js`) — so a theme is switched through those, never by setting `data-theme` alone; each theme block also declares its `color-scheme` in CSS, because the build compiles `light-dark()` into variables that declaration switches. CSS that differs for every dark theme asks `:root[data-scheme='dark']`, not each theme by name. Paper's values sit on `:root`; Dark, Midnight and High contrast override them in `src/styles/themes.css`, every token in every theme (`src/app/__tests__/theme.test.ts` checks that, and 4.5:1 for text). What is drawn outside CSS — Unigraph's engine, Plotly, the slide layer — reads `themeTokens()` and redraws on `onThemeChange` / `useTheme` (`src/app/theme.ts`). Colours that are data (a type's, a tag's, a palette) are not the theme's. A new theme is a block in `themes.css`, an entry in `THEMES` and one in `public/theme-boot.js` (which applies the choice before the first paint).
- **Every modal is ours, and keyboards reach it.** A dialog is `components/ui/Dialog` (or `ConfirmDialog`), never `window.confirm`/`alert`/`prompt`: it moves focus in when it opens, keeps Tab inside, and gives focus back when it closes; a `danger` confirm starts on Cancel, so Enter on a dialog that just opened deletes nothing. A question a tool or the bridge asks (`guarded`) starts on Cancel whatever it is, and its yes waits 500 ms after it appears or changes (`components/ui/useArmed.ts`); such questions queue, never replace one another. A notice is `useToast`, which speaks through a live region. Faint text stays at 4.5:1 (`--text-faint`), and keyboard focus is always drawn (the global `:focus-visible` ring in `index.css`) — don't take an outline away without drawing another.
- **Benchmarks do not live here.** A file that measures how fast something is — 200k entities generated and indexed, the pack against JSON, a store holding a million — is not a test and does not belong in `src/**/__tests__`, where it slows every run and fails on a busy machine. Keep it outside the repo while you are measuring, and delete it when you are done.
- **The slow tests measure work, not the machine.** They do real volumes or real waiting — 200k generated entities, a hundred thousand hashed ids, a twenty-thousand-entity search, a JSONL stream, the physics simulation, the sandbox's memory cap, the bridge's child processes over websockets — and each declares its own generous timeout, because a bare five-second harness limit only ever measures how busy the laptop is. What has to hold is in their assertions. On a loaded machine (several sessions, a headless browser or two) expect them to fail anyway: rerun them alone, or the whole suite with `npx vitest run --no-file-parallelism`, before reading anything into it, and say in the commit which you did. To find a test that still leans on the harness default rather than declaring what it needs, run the suite with the limit pulled in — `npx vitest run --testTimeout=2500` — and give a budget to whatever times out on a wait it takes deliberately. As of this writing nothing does but one chat test in `features/assistant`.
- **Two hosts, one tool set.** The tools run in a tab (the assistant, the bridge) and in Node (`src/headless`, driven over MCP). Logic a tool needs belongs in `src/core/` where both reach it, not in the tool file: the explorer's `graph_style` and the engine's `graph_scene` share `core/graph/styleChannels.ts` for exactly that reason. Anything a browser owns — a camera, a canvas, a player — stays in the tab, and the headless engine leaves the tool out.
- **MCP parity.** A feature reachable from the UI must also be reachable over MCP, and a change to a feature's behaviour is a change to its tool: a tool in `src/features/assistant/*Tools.ts`, added to `createAppTools` in `tools.ts` and to the sorted name list in `__tests__/assistant.test.ts`, with a test that runs it. When a UI action gains an option, the tool gains the parameter; when a data shape changes (a new `data` key the app reads), the tool that writes it and the spec that describes it change in the same commit. The tool reference on `/docs/assistant` is generated from the manifest, so a good `description` and parameter descriptions are the documentation.
- **Documentation parity.** A change a user can see is not done until the documentation says so, in the same commit: the relevant page in `src/docs/*.md` (a new concept gets a section; a new page is registered in `src/features/docs/pages.ts`), the *What is built* list in `src/docs/about.md` for a new capability, `README.md` for a new module or a changed architecture, and `public/spec` + `src/core/exchange/ae/aegraph-v1.schema.json` + `src/docs/spec.md` for anything that changes what a file can carry. `src/features/docs/AGENTS.md` has the checklist. Prose is written for the reader of the app, present tense, saying what it does and why it is shaped so — not a changelog.
- **Agent guides parity.** When you add an area, a page, a tool file or a convention, add it to the `AGENTS.md` of that area (and this table when it is a new area). These files are how the next session understands the code without reading all of it.
- Tools that put data on screen should also put it in the ES: `globe_load`, `add_path`, `import_graph`, `diagram_to_dataset` are the pattern.
- Verify in the running app, not just by tests: `GL=1 node mcp/drive.mjs <steps.mjs> http://localhost:5199/` drives a headless tab through the bridge (`call(name, args)`, `evaluate`, `shot`, `send` for raw CDP — good for profiling with `Profiler.*`). Software WebGL makes context creation seconds slow there — see `docs/proposals/performance-2026-09-17.md`. A `vite preview` of `dist/` on another port is the stable target when the dev server is mid-reoptimisation.
- Performance is a feature: a change to a page that redraws (maps, globe, graph, tables) is measured before it is merged — long tasks under interaction, render counts, a CPU profile — and the numbers go in the commit message.
- A user's Library may hold private data: print aggregates only, never content, and never commit anything derived from it.
- Locally (localhost / 127.0.0.1) the chat is Claude Code over the bridge only: `hasApiCredentials` is false and `createClient` throws `LocalOnlyError` there, whatever key is present. Keep it that way. On a deployed copy the chat is Claude Code over the bridge or the user's own Anthropic key, sent straight from the browser — there is no sign-in, proxy or server key, and none is to be added. Voice locally is OpenAI through the dev server's `/api/openai` (the key in `.env.local`).
